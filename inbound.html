INBOUND · RECEIVING

让计划到仓的货物，经过收货与上架进入库存

Inbound 管理货物进入仓库的过程。Receipt 记录预计到货内容并承接现场收货；客户退货则先通过 RMA 明确退回商品，再以 RMA 类型 Receipt 完成实际入库。

常规到货按 Receipt 组织收货

记录客户、到货参考信息和预计 SKU，再生成 Receiving Task 供现场执行。

客户退货先授权，再接收入库

RMA 审批通过后建立退货 Receipt，实收数量随收货结果回写 RMA。

转移入库承接调拨或产权转移

转移类 Receipt 关联对应 Transfer Order，继续沿用收货、上架和库存形成流程。

01建立入库来源普通到货直接创建 Receipt；退货先创建并审批 RMA
→
02执行 Receiving Task现场完成收货步骤，并在 LP Setup 记录实际商品和数量
→
03形成待上架库存收货任务关闭后，根据已记录的 LP 内容创建库存
→
04上架并完成入库Put Away Task 将货物移入库位，Receipt 按客户设置关闭
01
INBOUND · RECEIPT

用 Receipt 连接到货计划与现场收货

Receipt 用来管理一批预计到仓的货物。仓库先记录客户、到货来源和预计商品，货物抵达后再以 Receipt 创建收货任务，核对实际到货并推进上架，最终形成库存。

页面预览

从列表掌握待收货单据及任务进度

状态汇总用于查看 Open、In Progress、Closed 和 Exception 的数量；列表同时显示 Receipt Type、Receive Task 与 Put Away Task，便于追踪每张单据所处阶段。

核心场景

供应商通知一批货物即将到仓

例如客户安排一批商品通过承运商送达仓库。操作人员先建立 Receipt，记录这批货属于哪个客户、采用哪种入库类型、预计何时到达，并列出计划接收的 SKU 和数量。货物到仓后，现场人员直接依据这张单据创建 Receiving Task，不需要重新录入到货资料。

单据归属Customer · Receipt Type · Reference

确定货物属于哪个客户、采用哪类入库场景，并以 Reference 记录本次到货的外部识别信息。

运输与预约Container · BOL · Carrier · Appointment

按实际需要记录集装箱、提单、封签、Tracking、承运商和进场预约资料；Is Rush 标记需要优先处理的到货。

按到货场景选择 Receipt Type

Receipt Type 位于 Basic Information，用来说明货物为什么进入仓库，并决定是否需要关联前置单据：

供应商或客户安排普通到货Regular Receipt

直接登记客户、到货信息和预计商品，不要求关联额外来源单据。

客户将商品退回仓库RMA Receipt

先选择已经审批的 RMA，再进行实物收货；退回库存按 Return Channel 记录并要求外观检验。

产权转移入库Title Transfer Receipt

用于货权转移产生的入库，需要关联对应的 Transfer Order。

MIGO 转移入库MIGO Transfer Receipt

用于 MIGO 转移场景，需要关联对应的 Transfer Order。

仓内或仓间内部调拨Internal Transfer Receiving

用于内部调拨的接收入库，需要关联对应的 Transfer Order。

货权与商品Title · SKU

Title 确定这批库存的货权方，SKU 确定实际计划接收的商品。

预计数量Qty · UOM

记录预计接收数量及其计量单位，供后续现场收货时核对。

供货来源Supplier

需要追踪供货方时，选择该批商品对应的 Supplier。

货物到仓之后

库存以现场实收记录为准

保存 Receipt 不会直接增加库存。货物到仓后，实际收到的 LP、SKU 和数量在 Receiving Task 中登记；任务完成时，系统据此更新 Received Qty 并形成待上架库存。

01手持端操作 · Receiving Task登记实收结果

现场人员通过 LP Setup 记录实际 LP、SKU 和数量。

→
02系统自动处理 · Inventory形成待上架库存

任务完成后，系统按实收结果建立库存，并继续进入 Put Away。

没有实收记录如果任务中没有完成任何 LP Setup，即使强制关闭也不会产生库存；强制关闭后的 Receipt 进入 Exception，而不是正常 Closed。

取消条件 Receipt 仅在 Open 且尚未开始收货时可以取消；收货任务开始后将不能取消。

02
INBOUND · RMA MANAGEMENT

先确认退货范围，再安排商品返仓

RMA 用来管理客户退货申请。它先明确由哪个客户退回哪些商品、预计数量及退货原因；审批通过后，仓库才能建立 RMA 类型 Receipt，接收实物并将实收结果回写到退货记录。

核心场景

客户申请退回一批已发出的商品

例如零售客户需要退回两种商品。仓库在商品到达前先建立 RMA，记录客户、退货类型、商品、预计数量和原因，并完成内部审批。这样现场人员能够提前知道哪些商品获准返仓，而真正的库存仍要等退货 Receipt 收货后才产生。

退货主体谁要退货

Customer 确定本次退货属于哪个客户。

授权范围允许退回什么

SKU Lines 记录商品、UOM 和 Expected Qty。

业务依据为什么退回

RMA Type 和 Return Reason 说明退货来源与原因。

建立退货授权

记录本次允许退回的商品范围

RMA No 和 RMA Type 用于识别退货申请，SKU Lines 记录计划退回的商品、UOM、预计数量和原因。Original Order ID 可补充原订单线索，但当前不是必填项，也不会自动限制退货数量不得超过原出库数量。

从授权到实际入库

RMA 决定能否收，Receipt 负责实际怎么收

提交申请Open｜等待审批

RMA 只记录退货计划，此时可以审批或取消，不会创建库存。

→
允许返仓Approved｜可创建 Receipt

审批通过后，仓库以该 RMA 建立退货类型 Receipt。

→
接收实物In Progress｜回写实收数量

Receiving Task 的实收结果更新 Received Qty，Receipt 关闭后完成退货入库。

创建退货收货单时，将 Receipt Type 设为 RMA Receipt，再选择本次收货所依据的 RMA。

取消边界 RMA 只有在 Open 状态可以取消；一旦已创建 Receipt 并进入 In Progress，就不能再取消原 RMA。

01
OUTBOUND · OUTBOUND ORDER

先把客户的发货要求转成仓库可以执行的订单

Outbound Order 是出库作业的起点。它记录本次订单属于哪个客户、需要发出哪些商品和数量、送往哪里、由谁承运以及计划何时完成；库存锁定、拣货、包装和装车都以这些订单资料为依据。

从列表掌握待处理订单与当前进度

顶部汇总区显示 Imported、Processing、Shipped 和 Total；订单列表进一步显示 Order Plan 与 Status，用于判断订单是否尚待处理、库存承诺受阻、已经进入计划或完成发运。

核心场景

客户要求仓库把一批商品发往指定收货地址

操作人员先选择 Customer，确认订单类型与运输要求，再填写 Ship To Address 和计划时间，最后添加 SKU Lines。订单保存后形成出库需求，但此时还没有扣减库存；后续 Inventory Commitment 才会为订单匹配并锁定可用库存。

订单归属谁要发货

Customer 确定订单归属，并影响后续库存分配策略和 Load 分组。

发货内容发什么、发多少

SKU Lines 记录 Item、UOM、Title 和 Qty，作为库存匹配与数量换算依据。

履约要求发到哪里、如何运输

Address、Carrier、Ship Method 和时间字段共同描述交付要求。

Customer订单所属客户，决定可选商品及适用的库存分配策略。
Retailer订单对应的零售渠道或门店体系。
Order Type出库业务类型，如 Regular Order。
Reference No客户或上游系统提供的业务参考编号，用于查询与对账。
Sales Order No关联的销售订单编号。
PO No关联的采购订单编号。
Batch No出库订单的批次编号，用于归集同批导入或同批处理的订单。
Master Tracking No整票货件或主包裹的总追踪编号。
Source订单来源，如页面手工创建或接口导入。
Signature Type承运交付时要求的签名服务类型。
Total Weight整张订单的预计总重量，供运输安排参考。
Total Pallets整张订单预计使用的托盘数量。
Consolidation No需要合并处理的订单所使用的归集编号。
Priority订单的业务优先级，供后续计划与派发使用。
Single QTY标识订单是否属于单件数量场景，由系统根据订单内容显示。
运输安排

Carrier 表示实际承运商，Ship Method 决定订单采用的运输场景：Truckload（整车）、Less Than Truckload（零担）、Will Call（客户自提）或 Small Parcel（小包裹）。Delivery Service、Freight Term 和运输单号用于补充具体交接要求。

履约时间

Schedule Date、Ship Not Before / Later 和 Appointment Time 用来描述计划作业及允许发货的时间窗口；Shipped Time、Canceled Date 等由后续状态记录实际结果。

Address

Ship From 表示本次发货方，Ship To 表示实际收货目的地，Bill To 用于账单资料。选定后地址内容随订单保存，后续主档修改不会改变该订单。

SKU Lines

SKU 确定商品，UOM 与 Qty 表示需求数量，Title 限定货权。Inventory Commitment 会按照这些条件匹配并锁定库存；保存订单本身不会直接扣减库存。

02
OUTBOUND · INVENTORY COMMITMENT

在订单进入拣货前，确认库存是否能够兑现需求

Inventory Commitment 将 Outbound Order 的需求与当前可用库存进行匹配。它先显示订单行的库存缺口，再由用户执行锁定；锁定结果会直接更新订单状态，并决定订单能否继续进入拣货计划。

核心场景

先看缺口，再决定哪些订单可以进入履约

当多个订单同时等待出库时，操作人员可以先预览每个 SKU 的需求、已锁定数量和缺口数量，判断库存不足会影响哪些订单，再执行 Commit。库存充足的订单进入 Committed；只有部分库存可用时进入 Partial Committed。

01 · 检查Gap Preview

查看订单行的需求数量、已锁定数量和缺口数量。

→
02 · 锁定Commit

按订单优先级和库存匹配规则立即创建 ACTIVE 库存锁。

→
03 · 结果Committed / Partial Committed

订单根据锁定结果更新状态，继续等待后续计划。

Build Commitment：选择订单并执行库存锁定

页面按 Order ID、Order Type、Status、Customer、Carrier、Ship Method 和 Schedule Date 筛选待处理订单。选中订单后，可先查看 Gap Preview，再点击 Commit 立即执行锁定。

Gap Preview 关注的数量关系
需求数量订单要求发出的数量。
已锁定数量当前已经成功占用的库存数量。
缺口数量仍未匹配到库存的数量。
Commitment Report：查看与回滚已建立的库存承诺

报告按订单、客户、状态、承运商和 Batch No 查询已建立的承诺。只有 Committed 或 Partial Committed 订单可以 Rollback；回滚后库存锁释放，订单回到 Open。

03
OUTBOUND · ORDER PLANS

把待出库订单组织成可执行的拣货计划

Order Plans 将一个或多个已承诺库存的订单打包到同一个计划中，并指定该计划使用的 Pick Method、Pick Mode 和 Task Priority。计划创建后释放，系统据此生成拣货任务。

核心场景

从已承诺订单到可执行任务

当一批订单完成库存锁定后，计划员需要决定这些订单的拣货策略——是逐单拣还是合并拣、用人工推车还是 AGV，以及优先级如何。Order Plans 就是这个决策的执行入口。

01 · 创建Create Plan

选择拣货方法和模式，添加待处理订单。

→
02 · 释放Release

计划释放后，系统自动生成拣货任务。

→
03 · 执行Pick Tasks

拣货人员或设备按任务执行拣货作业。

Create Plan：配置拣货策略并关联订单

创建计划时先确定 Pick Method 和 Pick Mode，再从已承诺库存的订单中选择要纳入本次计划的订单。

Pick Method

决定订单如何分配到拣货任务。

Single Order Pick一个订单对应一个拣货任务。适合大件商品、高价值订单或定制化包装。
Batch Order Pick多个订单合并到一个任务，一次路线拣取多单商品，再按订单拆分。
Wave Pick by Item汇总多个订单中相同 SKU 的需求，按商品集中拣取。
Pick Mode

指定拣货时使用的设备或工位方式。

Pick to Wall批量拣取后，在播种墙按订单投放到对应格口。
Pick by Tote Cart使用多层推车边拣边按订单分配到不同 Tote。
Pick by AGV由 AGV 将货架送至固定工位，采用货到人方式拣货。
其他配置
Task Priority影响任务在拣货队列中的顺序。
Max Order Qty Per Pick Task限制单个任务可包含的订单数量。
Assignment Mode / Default Assignee决定任务采用手动或自动指派，并可设置默认执行人。
Pick From VLGs限定拣货库存的来源区域。
Plan Tags为计划添加标签，便于后续筛选分类。

Order Dispatch 把订单筛选、库存锁定、Order Plan 与拣货任务创建连接起来。Order Filters 决定处理哪些订单；Dispatch Settings 决定拣货方式、任务拆分、异常处理和执行时间。

ORDER FILTERS圈定待处理订单

按状态、类型、客户、承运商、运输方式和时间等条件建立筛选模板。

→

→
EXECUTION RESULT生成计划和拣货任务

系统锁定库存，将符合条件的订单纳入 Order Plan，并按设置生成拣货任务。

04.1
ORDER DISPATCH · ORDER FILTERS

用筛选模板定义哪些订单可以进入 Dispatch

Order Filters 保存可重复使用的订单条件。Dispatch 只处理满足条件且尚未关联 Order Plan 的订单。

核心场景

为不同履约场景准备独立的订单入口

小包裹订单可按 Ship Method 和订单状态建立模板；内部调拨或退货订单可按 Order Type 分开处理。不同字段同时填写时需全部满足，同一字段多选时匹配任一值。

Order Status订单当前状态

选择 Open、Imported 或其他待处理状态。

Order Type业务类型

区分 Regular、Dropship、Internal Transfer 和 Return Goods。

Carrier / Ship Methods运输属性

区分 Small Parcel、LTL、Truckload 或 Will Call。

Retailer / Ship To零售商和收货方

按门店、渠道或配送区域归集订单。

Single Item / Order Qty订单结构和数量

筛选单品订单、批量订单或数量范围。

Data Channel / Freight Term来源和运费条款

按订单来源或运费责任区分履约方案。

MABD / Ship No Later履约期限

优先筛选临近截止日期的订单。

Appointment / Shipped Time时间范围

按预约或发运时间查询订单。

Dynamic Text Value自定义动态字段

按客户项目号、渠道标识等动态值筛选。

系统会排除已经关联 Order Plan 的订单，避免重复 Dispatch。

04.2

定义筛选后的订单如何形成计划与任务

同一批订单，按仓库作业方式生成不同任务

05
OUTBOUND · SMALL PARCEL STATION

拣货完成后，在工位完成扫描核验、打包和面单打印

Small Parcel Station 是小包裹出库的打包工位。操作员扫描已拣货的容器或任务调出订单，核对商品，录入包裹信息并打印面单，完成包裹从仓内作业到承运商交接的准备。

核心场景

已拣货的容器到达小包裹工位，需要完成一票订单的打包发运

拣货在手持端完成后，容器被送到打包工位。操作员在这里调出订单，确认每件商品与数量，补充包裹尺寸和重量，最后打印 Shipping Label 和需要随货附上的装箱单。

01

左侧扫描框：调出订单

扫描 LP、Task ID、Tote Cart 或 Tracking No，系统根据对应关系调出订单及待打包物料；已发货的 Tracking No 用于只读重打面单。

LP / Task ID调出当前待打包订单。
Tote Cart按推车关联的 Tote 和 LP 批量查找订单。
Tracking No进入 Reprint 模式查看已发货记录。
02

右侧扫描框：逐件核验

逐件扫描 UPC、Item Name、Case UPC 或其他商品编码，系统将扫描结果与当前订单物料匹配并扣减待扫数量。

UPC / Item确认商品属于当前订单。
Case UPC按整箱换算数量一次性确认。
SN / Lot No按订单和商品规则校验序列号或批次。
03

Print All：完成包裹单据

全部物料核验完成并录入包裹尺寸、重量后，选择需要的单据并点击 Print All。

Shipping Label（默认勾选）物流面单，包含收发件信息和运单条码。适用于交接承运商的所有包裹，每个包裹打印一张。
Packing List by Order按订单汇总商品和数量，不区分商品装在哪个包裹。适用于客户按订单核对收货内容。
Packing List by Shipping按包裹分别列出所装商品。适用于一票订单拆成多个包裹发货，方便收货方确认每箱内容。
06
OUTBOUND · LOAD MANAGEMENT

把待发订单组织成可交接给承运商的装载批次

Load Management 归集同一次运输中的出库订单，维护承运商、地址、预约时间和运输编号。Load Task 必须基于已有 Load 创建；Task > Load Tasks 只管理和执行已创建的任务。

核心场景

一辆预约到仓的车辆，需要一次带走多个订单

例如承运商安排一辆整车下午 3 点到仓，同时提取三个已完成拣货的客户订单。仓库用一个 Load 归集它们，统一记录 Carrier、预约时间、Ship From / Ship To、Master BOL No 和 PRO No。

状态概览

New、In Progress、Loaded 和 Shipped 反映装载批次所处阶段。

运输查询

按 Load、状态、类型、Customer、Carrier、BOL 和时间范围定位批次。

任务关联

Load Tasks 列显示已创建的现场任务编号。

任务创建入口

Load Task 必须基于已有 Load 创建

在 Load Management 列表勾选 Load 后点击 Create Task。Task > Load Tasks 当前不支持手工新建，只管理和执行已经创建的任务。

Dock / Load Mode月台和装车方式。
Carrier / Equipment Type承运商及设备类型。
Priority / Assignee优先级和负责人。
Selected Loads本次任务包含的 Load。

记录本次装载的运输安排

Customer / Carrier所属客户和承运商。
Load TypeFTL、LTL、SPL、CONSOL、IMDL 或 TRANSLOAD 分类。

Master BOL No / PRO No主提单和货运追踪编号。
ARN装载参考编号。
Note / Consignee Note内部及收货方备注。
地址与订单

确认运输地址，并加入本次装载的订单

运输地址

Ship From、Ship To 和 Bill To

保存本次 Load 的发货、收货和账单地址快照。

Order Lines

选择本次装载包含的出库订单

可加入 Picked、Packed、Palletized 或 Ready to Ship 的订单，并可启用装载顺序。

OUTBOUND · SHIPMENT TICKETS

记录订单实际发运结果，并向客户系统发送 Delivery Confirmation

Shipment Ticket 是订单级的发运结果记录。系统在 Load Task 关闭后，根据订单、运输方式、Tracking No 和 Load 对已发运库存进行分组并自动生成。每张 Ticket 记录本次发出的 LP、Tracking No 等信息，并作为打印 Packing List 和发送 DC（Delivery Confirmation）的数据入口。

核心场景

货物离开仓库后，通知客户系统“已发货”

装车任务关闭后，仓库需要保留正式发运记录，说明哪些商品、装在哪些容器中、通过什么运单号发出；客户的 OMS / ERP 也需要接收发货确认并更新订单状态。Shipment Ticket 就是这份记录和通知的数据载体。

01 · 触发Close Load Task

装车任务关闭，系统自动生成发运记录。

→
02 · 生成Auto Create Ticket

按订单分组，记录 LP 和 Tracking No。

→
03 · 通知Send DC

将发运信息推送至客户 Webhook。

页面用途

查询已生成的发运记录，并处理后续单据与通知

列表用于按订单、Load、Tracking No 等条件定位 Ticket。进入对应记录后，可核对本次实际发出的 LP 和商品，并根据需要打印 Packing List 或执行 Send DC。

DC · Delivery Confirmation

向客户或上游系统发送完整发运结果

DC 包含订单、商品、数量、LP、Tracking No、Carrier、地址及 BOL / MBOL 等发运信息。发送前必须在对应 Customer Settings 中配置可用的 Webhook Channel。

前置配置

Customer Settings → Webhook Channels

MDM → Customer → Settings → 自动化与数据连接 → Webhook Channels

Channel Name
Send DC 时选择的目标通道。
API URL
客户接收 DC 数据的 HTTP 接口地址。
Event Types
必须包含 ORDER_SHIPPED。
Enabled
关闭后不显示在 Send DC 通道列表中。
Headers / Secret
用于接口认证和 HMAC 签名校验。
Max Retry
发送失败后的最大重试次数。

未配置已启用 Channel 的客户无法执行 Send DC。
