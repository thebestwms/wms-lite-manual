转移入库承接调拨或产权转移

转移类 Receipt 关联对应 Transfer Order，继续沿用收货、上架和库存形成流程。

01
INBOUND · RECEIPT

用 Receipt 连接到货计划与现场收货

Receipt 用来管理一批预计到仓的货物。仓库先记录客户、到货来源和预计商品，货物抵达后再以 Receipt 创建收货任务，核对实际到货并推进上架，最终形成库存。

核心场景

供应商通知一批货物即将到仓

例如客户安排一批商品通过承运商送达仓库。操作人员先建立 Receipt，记录这批货属于哪个客户、采用哪种入库类型、预计何时到达，并列出计划接收的 SKU 和数量。货物到仓后，现场人员直接依据这张单据创建 Receiving Task，不需要重新录入到货资料。

页面预览

从列表掌握待收货单据及任务进度

状态汇总用于查看 Open、In Progress、Closed 和 Exception 的数量；列表同时显示 Receipt Type、Receive Task 与 Put Away Task，便于追踪每张单据所处阶段。左上角的 Presets 可以把当前设好的一组筛选条件保存为预设，下次在下拉中直接选用，适合每天重复使用的查单口径。

单据归属Customer · Receipt Type · Reference

确定货物属于哪个客户、采用哪类入库场景，并以 Reference 记录本次到货的外部识别信息。

运输与预约Container · BOL · Carrier · Appointment

按实际需要记录集装箱、提单、封签、Tracking、承运商和进场预约资料；Is Rush 标记需要优先处理的到货。

按到货场景选择 Receipt Type

Receipt Type 位于 Basic Information，用来说明货物为什么进入仓库，并决定是否需要关联前置单据：

供应商或客户安排普通到货Regular Receipt

直接登记客户、到货信息和预计商品，不要求关联额外来源单据。

客户将商品退回仓库RMA Receipt

先选择已经审批的 RMA，再进行实物收货；退回库存按 Return Channel 记录并要求外观检验。

产权转移入库Title Transfer Receipt

用于货权转移产生的入库，需要关联对应的 Transfer Order。

MIGO 转移入库MIGO Transfer Receipt

用于 MIGO 转移场景，需要关联对应的 Transfer Order。

仓内或仓间内部调拨Internal Transfer Receiving

用于内部调拨的接收入库，需要关联对应的 Transfer Order。

货权与商品Title · SKU

Title 确定这批库存的货权方，SKU 确定实际计划接收的商品。

预计数量Qty · UOM

记录预计接收数量及其计量单位，供后续现场收货时核对。

供货来源Supplier

需要追踪供货方时，选择该批商品对应的 Supplier。

货物到仓之后

库存以现场实收记录为准

保存 Receipt 不会直接增加库存。货物到仓后，实际收到的 LP、SKU 和数量在 Receiving Task 中登记；任务完成时，系统据此更新 Received Qty 并形成待上架库存。

01手持端操作 · Receiving Task登记实收结果

现场人员通过 LP Setup 记录实际 LP、SKU 和数量。

→
02系统自动处理 · Inventory形成待上架库存

任务完成后，系统按实收结果建立库存，并继续进入 Put Away。

没有实收记录如果任务中没有完成任何 LP Setup，即使强制关闭也不会产生库存；强制关闭后的 Receipt 进入 Exception，而不是正常 Closed。

取消条件 Receipt 仅在 Open 且尚未开始收货时可以取消；收货任务开始后将不能取消。

INBOUND · RECEIPT FILTER TEMPLATES

把常用的收货单筛选条件存成模板，一键套用

Receipt Filter Templates 用来保存 Receipt 列表里反复使用的筛选组合。模板建好后，在 Receipt 列表左上角的 Presets 中选用，不必每次重新逐项设置。

核心场景

每天开工先看同一批单据

例如收货组长每天都要先处理加急到货，或只看某个客户处于 In Progress 的单据。把这些条件存成模板后，便于不同班次用同一套口径查单。

在列表里管理已有模板

Selected Fields 概括了每个模板包含哪些条件，名称建议体现用途，方便同事一眼选对。点击 Create Filter Template 新建。

先命名Basic Information

填写模板名称，并用 Note 说明适用场景。

再挑条件Supported Fields

在左侧勾选要用的筛选项，右侧会出现对应的条件输入。

设定取值Filter Criteria

为每个条件选择匹配方式并填写值，保存后到 Receipt 列表左上角的 Presets 中选用。

模板只保存筛选条件，不会改动任何 Receipt 数据。

03
INBOUND · RMA MANAGEMENT

先确认退货范围，再安排商品返仓

RMA 用来管理客户退货申请。它先明确由哪个客户退回哪些商品、预计数量及退货原因；审批通过后，仓库才能建立 RMA 类型 Receipt，接收实物并将实收结果回写到退货记录。

核心场景

客户申请退回一批已发出的商品

例如零售客户需要退回两种商品。仓库在商品到达前先建立 RMA，记录客户、退货类型、商品、预计数量和原因，并完成内部审批。这样现场人员能够提前知道哪些商品获准返仓，而真正的库存仍要等退货 Receipt 收货后才产生。

退货主体谁要退货

Customer 确定本次退货属于哪个客户。

授权范围允许退回什么

SKU Lines 记录商品、UOM 和 Expected Qty。

业务依据为什么退回

RMA Type 和 Return Reason 说明退货来源与原因。

建立退货授权

记录本次允许退回的商品范围

RMA No 和 RMA Type 用于识别退货申请，SKU Lines 记录计划退回的商品、UOM、预计数量和原因。Original Order ID 可补充原订单线索，但当前不是必填项，也不会自动限制退货数量不得超过原出库数量。

从授权到实际入库

RMA 决定能否收，Receipt 负责实际怎么收

提交申请Open｜等待审批

RMA 只记录退货计划，此时可以审批或取消，不会创建库存。

→
允许返仓Approved｜可创建 Receipt

审批通过后，仓库以该 RMA 建立退货类型 Receipt。

→
接收实物In Progress｜回写实收数量

Receiving Task 的实收结果更新 Received Qty，Receipt 关闭后完成退货入库。

创建退货收货单时，将 Receipt Type 设为 RMA Receipt，再选择本次收货所依据的 RMA。

取消边界 RMA 只有在 Open 状态可以取消；一旦已创建 Receipt 并进入 In Progress，就不能再取消原 RMA。

OUTBOUND · OUTBOUND ORDER

先把客户的发货要求转成仓库可以执行的订单

Outbound Order 是出库作业的起点。库存锁定、拣货、包装和装车都以订单资料为依据，订单也可由客户系统通过接口导入。

核心场景

客户要求仓库把一批商品发往指定收货地址

操作人员选择 Customer，确认订单类型与运输要求，补充收货地址和计划时间，最后添加 SKU Lines。订单保存后只形成出库需求，不会扣减库存；后续 Inventory Commitment 才会为订单匹配并锁定可用库存。

订单列表

一眼看清订单进行到哪一步

顶部汇总区快速反映待处理与已发运的订单规模；列表里的 Order Plan、Pick Task、Pack Task、Load Task 几列，能直接看出订单已经进入哪个环节，不必再逐个任务页面去查。

批量处理：勾选多张订单后，可在 Actions 中批量取消、关闭、挂起、解除挂起或回滚；常用的查询条件可存为 Presets，需要对账时用 Export 导出。

Create Order

创建订单时先确定归属与运输方式

Customer 决定可选商品和库存分配策略；Order Type 与 Ship Method 决定后续走哪条履约路径，例如 Small Parcel 订单会进入小包裹打包工位，整车和零担订单则通过 Load 交接承运商。

01
时间窗口

Schedule Date 安排计划作业日，Ship Not Before 与 Ship No Later 限定允许发货的区间，需要预约承运商时再填 Appointment Time。

02
地址随单保存

Ship From、Ship To、Bill To 选定后作为快照保存在订单中，之后修改地址主档不会影响已创建的订单。

03
SKU Lines

通过 Add Item Lines 添加商品，UOM 与 Qty 表示需求数量，Title 用来限定货权，是库存锁定的匹配依据。

Order Detail

订单创建后，在详情页继续跟进

详情页在创建页的基础上增加了订单状态，并提供 Print 和 Actions 等操作入口。Status、Source 这类由系统维护的信息以灰色只读显示，不能手工改动。

执行记录：订单创建后，详情页还会出现 Picked Inventory、Parcels、Shipment 和 Put Back History 四个页签，分别记录已拣货的库存、包裹与运单信息、发运结果和退回上架记录。它们随作业进度才有内容，多数订单只会用到前几项，Put Back History 通常为空。

Dynamic Fields

承接客户自定义的业务信息

当客户有标准字段无法容纳的信息，如项目编号、内部分类或特殊处理标记，可以放在 Dynamic Fields 中随订单保存。它提供文本与日期两类自定义字段，字段含义由客户和仓库自行约定。

02
OUTBOUND · INVENTORY COMMITMENT

在订单进入拣货前，确认库存是否能够兑现需求

Inventory Commitment 把订单需求与当前可用库存对上号：先看缺口，再锁定库存，锁定结果决定订单能否继续进入拣货计划。

核心场景

多张订单同时等待出库，库存不一定够所有人

操作人员先在 Build Commitment 中查出待处理订单，用 Gap Preview 判断哪些订单缺货、缺多少，再决定是否执行 Commit。库存不足的订单会停在 Commit Blocked 等待补货，不会占用其他订单的库存；已锁定的订单可以在 Commitment Report 中查看，必要时回滚释放。

Build Commitment

选出要锁定库存的订单

Status 筛选决定处理哪一类订单：Open 与 Imported 是等待首次锁定的订单，Commit Blocked 和 Commit Failed 则是上次尝试未成功、需要重新处理的订单。勾选订单后，可先预览缺口，再点击 Commit 立即锁定。

Gap Preview

锁定之前，先知道缺多少

弹窗按订单行对比需求数量与可用数量，Shortage Base Qty 为红色标记的行就是库存不足的商品。可以据此提前安排补货或调整订单，避免提交后才发现被阻塞。预览只做检查，不会锁定库存。

Commitment Report

查看已经建立的库存承诺

订单锁定后会进入 Committed，并随着计划、拣货、打包、发运逐步更新状态，所以这里也可以当作订单履约进度的查询入口。订单需要重新分配库存时，勾选后使用 Rollback 释放已锁定的库存。

03
OUTBOUND · ORDER PLANS

把已锁定库存的订单组织成可执行的拣货计划

Order Plan 决定一批订单怎样被拣、由谁拣、先拣哪一批。计划释放后，系统据此生成拣货任务。

核心场景

一批订单完成库存锁定，需要决定现场怎么拣

计划员把订单纳入同一个计划，选择拣货方式（逐单拣还是合并拣）、拣货载具（推车、播种墙或 AGV）和任务优先级，再指定默认执行人。计划释放后，现场人员就能在手持端领取任务；整个计划的进度也都能在这里追踪。

计划列表

一眼看清每个计划走到哪一步

Status 反映计划从构建、生成任务到释放、完成的进度；orders、Pick Tasks 两列可直接看出计划规模，不必进入详情页逐个核对。

Create Plan

先定拣货策略，再添加订单

Pick Method 与 Pick Mode 是最关键的两项：前者决定订单如何分配到任务，例如一单一任务，或多单合并一次拣完再拆分；后者决定现场用什么方式拣，例如推车、播种墙或 AGV。设置好之后，通过 Add Orders 添加已锁定库存的订单即可创建。

01
控制任务规模

Max Order Qty Per Pick Task 限制单个任务包含的订单数量，避免任务过大、拣货员一次推车装不下。

02
指派方式

Assignment Mode 与 Default Assignee 决定任务是由系统自动分配，还是预先指给固定的拣货员。

03
限定拣货来源

Pick From Virtual Location Groups 可把拣货范围限制在指定区域，Plan Tags 则用于给计划打标签，便于后续筛选。

Plan Detail

计划创建后，在详情页跟进任务进展

详情页除 Basic Info 外，还有 Pick Strategies、Pick Tasks、Task Actions 和 Picked Inventory 四个页签，分别对应拣货策略、已生成的任务、任务操作记录和已拣出的库存。大多数情况下只需看 Basic Info 与 Pick Tasks，判断计划是否已释放、任务是否在正常推进。

04
OUTBOUND · ORDER DISPATCH

按预设条件批量推进订单进入拣货执行

Order Dispatch 把订单筛选、库存锁定、Order Plan 与拣货任务创建连接起来。Order Filters 决定处理哪些订单；Dispatch Settings 决定拣货方式、任务拆分、异常处理和执行时间。

ORDER FILTERS圈定待处理订单

按状态、类型、客户、承运商、运输方式和时间等条件建立筛选模板。

→
DISPATCH SETTINGS配置计划与任务规则

引用筛选模板，设置 Pick Method、Pick Mode、任务容量、自动释放和计划执行。

→
EXECUTION RESULT生成计划和拣货任务

系统锁定库存，将符合条件的订单纳入 Order Plan，并按设置生成拣货任务。

04.1
ORDER DISPATCH · ORDER FILTERS

用筛选模板定义哪些订单可以进入 Dispatch

Order Filters 保存可重复使用的订单条件。Dispatch 只处理满足条件、且尚未关联 Order Plan 的订单。

核心场景

不同履约场景，需要各自独立的订单入口

仓库往往同时处理几类订单：一件代发订单适合按商品汇总拣货，普通订单适合逐单拣货，小包裹订单则要走打包工位。为每一类订单建一个筛选模板，Dispatch 就能分别圈出对应的订单，互不干扰。

模板列表

一眼看清每个模板圈了哪些订单

Selected Fields 列直接显示模板用到的条件和取值，不必逐个打开就能区分模板的用途。同一类订单只需要维护一个模板，供不同的派单方案重复引用。

Add Order Filter

从左侧挑选条件，右侧设置取值

左侧 Supported Fields 列出所有可用的筛选条件，点选后会出现在右侧 Filter Criteria 中，再为它选择取值。条件越多范围越窄：不同条件需要同时满足，同一条件下选择多个值时，满足其中任意一个即可。保存之前可以用 Preview Orders 看一下当前条件能匹配到哪些订单。

建模板的思路：订单状态与订单类型通常是最基础的两项，再按承运商、运输方式或时间窗口收窄；需要按客户自定义字段区分订单时，可使用 Dynamic Text Value。已经关联 Order Plan 的订单会被自动排除，不会被重复派单。

04.2
ORDER DISPATCH · SETTINGS

定义筛选后的订单如何形成计划与任务

Dispatch Settings 把筛选模板和拣货配置组合成一个可执行的方案，可以手动执行，也可以按时间表自动运行。

核心场景

同一批订单，按现场作业方式生成不同的计划和任务

小件订单可以合并拣货、使用推车；自动化区域的订单可以交给 AGV。把这些做法分别保存成方案后，仓库只需要在合适的时间执行对应方案，或者让系统按时间表自动运行，不必每次手工创建计划。

方案列表

管理并执行仓库内的派单方案

每一行是一个方案。Auto Release 与 Schedule 两列的开关能直接看出方案是否会自动释放、是否按时间表运行。行尾的操作按钮依次是预览订单、立即执行、查看执行历史、复制和删除。

日常使用：新方案可以从相近的方案 Copy 后调整；执行前先用 Preview 确认会处理哪些订单；方案越多越要靠名称区分，建议把客户、拣货方式写进名称。

Add Dispatch Setting

按“订单来源、拣货方式、计划规模、执行时间”四步配置

页面从上到下分为六个区块，实际决策主要集中在这四件事上。

01
订单来源

Apply Filters 引用第一步建好的筛选模板，Customer 可进一步限定客户，Preview Orders 用来在保存前确认范围。

02
拣货方式

Pick Method 与 Pick Mode 决定订单如何合并成任务、由什么方式拣货；Task Priority、Assignment Mode、Default Assignee 决定任务的优先级和指派方式。

03
计划分组

Order Plan Group By 用来决定订单分组生成计划的依据，需要把不同订单分开作业时使用。

04
计划规模

Min Orders Per Plan 与 Max Orders Per Plan 控制一个计划至少、至多容纳多少订单，避免计划过碎或者过大。

05
自动释放与异常订单

开启 Auto Release 后计划生成即释放，现场可立刻领取任务。库存锁定失败的订单是否排除、带错误的订单是否移出计划并标记异常，也在这里选择，用于避免个别订单拖住整批作业。

06
执行时间

开启 Enable Schedule 后，可按固定间隔、每天、工作日或 Cron 表达式运行。页面会同步列出接下来的 10 次执行时间，保存前先核对时间是否符合预期。

Dispatch History

方案没有按预期生成计划时，先看历史

History 记录每次执行的结果：处理了多少订单、生成了多少计划、有多少订单锁定库存失败。没有生成计划时，Exception 列会说明原因，例如没有订单匹配筛选条件，就应回到 Order Filters 检查条件。

05
OUTBOUND · SMALL PARCEL STATION

拣货完成后，在工位完成扫描核验、打包和面单打印

Small Parcel Station 是小包裹出库的打包工位。操作员扫描已拣货的容器或任务调出订单，核对商品，录入包裹信息并打印面单，完成包裹从仓内作业到承运商交接的准备。

核心场景

已拣货的容器到达小包裹工位，需要完成一票订单的打包发运

拣货在手持端完成后，容器被送到打包工位。操作员在这里调出订单，确认每件商品与数量，补充包裹尺寸和重量，最后打印 Shipping Label 和需要随货附上的装箱单。处理完一票后，可以用 Reset 清空页面，再扫描下一票。

工位主页

上方调出订单，下方完成打印

页面顶部是扫描框和功能入口，扫描后订单与待打包的商品显示在中间区域，底部固定着可勾选的单据和 Print All。Operation Log 记录工位上的操作过程，需要回溯时可展开查看。

01

调出订单

扫描 LP、Task ID、Tote Cart 或 Tracking No，系统根据对应关系调出订单及待打包物料；已发货的 Tracking No 用于只读重打面单。

LP / Task ID调出当前待打包订单。
Tote Cart按推车关联的 Tote 和 LP 批量查找订单。
Tracking No进入 Reprint 模式查看已发货记录。
02

逐件核验

逐件扫描 UPC、Item Name、Case UPC 或其他商品编码，系统将扫描结果与当前订单物料匹配并扣减待扫数量。是否必须逐件扫描，由工位设置中的 Require Item Scan 控制。

UPC / Item确认商品属于当前订单。
Case UPC按整箱换算数量一次性确认。
SN / Lot No按订单和商品规则校验序列号或批次。
03

Print All：完成包裹单据

全部物料核验完成并录入包裹尺寸、重量后，选择需要的单据并点击 Print All。

Shipping Label（默认勾选）物流面单，包含收发件信息和运单条码。适用于交接承运商的所有包裹，每个包裹打印一张。
Packing List by Order按订单汇总商品和数量，不区分商品装在哪个包裹。适用于客户按订单核对收货内容。
Packing List by Shipping按包裹分别列出所装商品。适用于一票订单拆成多个包裹发货，方便收货方确认每箱内容。
工位设置

按本工位的作业习惯调整行为

点击右上角的 Settings 可以调整当前工位的作业方式，不同工位可以采用不同习惯。

三项开关与两台打印机

让扫描和打印更贴合现场

01
Require Item Scan

控制打包时是否要求逐件扫描商品。是否开启取决于现场对核验精度和打包速度的取舍。

02
Auto Print Label / Auto Close Order

两项都属于自动化选项，用来减少操作员的重复点击：前者与面单打印有关，后者与订单关闭有关。

03
ZPL Printer / PDF Printer

分别填写 ZPL 标签打印机和 PDF 文档打印机的名称，面单和装箱单可以输出到各自对应的设备。

其他入口

补发面单、处理异常、查看订单汇总

顶部另外三个入口用于特殊情况，日常打包通常不需要。

01
Reprint

面单损坏或需要补发时使用，针对已发货的包裹重新打印单据。

02
View Exception

集中查看被标记为异常的记录，没有异常时会显示 No exceptions。

03
Order Summary

需要先调出订单才能使用，用来查看当前订单的汇总信息。

06
OUTBOUND · LOAD MANAGEMENT

把待发订单组织成可交接给承运商的装载批次

Load Management 归集同一次运输中的出库订单，维护承运商、地址、预约时间和运输编号。装车现场的 Load Task 必须基于已有的 Load 创建。

核心场景

一辆预约到仓的车辆，需要一次带走多个订单

例如承运商安排一辆整车下午 3 点到仓，同时提取三个已完成拣货的客户订单。仓库用一个 Load 归集它们，统一记录承运商、预约时间、收发货地址和运输编号。车辆到达后，再基于这个 Load 创建装车任务，交给现场人员执行。

Load 列表

从装载批次的状态，判断今天的装车进度

顶部的状态汇总反映各阶段的批次数量，列表中的 Orders 列显示每个批次包含多少订单。Import 用于批量导入已有的装载数据，Export 用于导出列表，新建单个批次则点击 Add。

Create Load Task

装车任务从已有的 Load 创建

在列表中勾选 Load 后点击 Create Task，指定月台、装车方式，按需补充承运商和设备类型，再设置优先级和负责人。Task 菜单下的 Load Tasks 只用于管理和执行已经创建的任务，不能手工新建。

01
一次可选多个 Load

弹窗下方的 Selected Loads 会列出本次选中的批次，多个 Load 可以放进同一个装车任务。

02
必填项与优先级

Dock、Load Mode、Priority 和 Assignee 带红色星号，是创建任务必填的内容；需要加急的车辆可以调高 Priority。

New Load

先记录运输安排，再加入订单

创建页分为两部分：上半部分是承运商、运费条款、Load Type 和预约时间等运输信息；下半部分是 Ship From、Ship To、Bill To 三个地址和本次装载的订单行。Load Type 对应不同的运输方式，例如整车 FTL 与零担 LTL，按实际运输方式选择即可。

加入订单：通过 Add Order Lines 添加已完成拣货、等待发运的订单。需要按顺序装车时，可开启 Enable Load Sequence。地址会作为快照保存在这个 Load 中，之后修改地址主档不会影响已创建的批次。

Load 详情

创建之后，在详情页核对和跟进

详情页上方汇总运输信息和签收状态，下方的 Orders 页签列出本批次包含的订单，Photos 页签用于查看照片，没有照片时显示 No photos。右上角的 Print 用于打印单据，More Actions 中可以执行批次级别的操作，例如 Close Load。

07
OUTBOUND · SHIPMENT TICKETS

记录订单实际发运结果，并向客户系统发送 Delivery Confirmation

Shipment Ticket 是订单级的发运结果记录。装车任务关闭后，系统根据订单、运输方式、Tracking No 和 Load 对已发运库存分组并自动生成，同时作为打印 Packing List 和发送 DC（Delivery Confirmation）的数据入口。

核心场景

货物离开仓库后，通知客户系统“已发货”

装车任务关闭后，仓库需要保留正式的发运记录，说明哪些商品、装在哪些容器中、通过什么运单号发出；客户的 OMS 或 ERP 也需要收到发货确认，才能更新订单状态。Shipment Ticket 就是这份记录和通知的数据载体。

Ticket 列表

查询发运记录，并确认是否已通知客户

可以按 Ticket、订单、Load 或客户定位记录。DC Sent 一列用来判断发运结果有没有成功发送给客户系统，Status 则区分 Ticket 是新建还是已关闭。需要统一补发时，勾选多条记录后使用 Batch Send/Resend DC；需要对账时用 Export 导出。

DC · Delivery Confirmation

向客户或上游系统发送完整发运结果

DC 包含订单、商品、数量、LP、Tracking No、Carrier、地址及 BOL / MBOL 等发运信息。发送前必须在对应 Customer Settings 中配置可用的 Webhook Channel。

前置配置

Customer Settings → Webhook Channels

MDM → Customer → Settings → 自动化与数据连接 → Webhook Channels

Channel Name
Send DC 时选择的目标通道。
API URL
客户接收 DC 数据的 HTTP 接口地址。
Event Types
必须包含 ORDER_SHIPPED。
Enabled
关闭后不显示在 Send DC 通道列表中。
Headers / Secret
用于接口认证和 HMAC 签名校验。
Max Retry
发送失败后的最大重试次数。

未配置已启用 Channel 的客户无法执行 Send DC。
