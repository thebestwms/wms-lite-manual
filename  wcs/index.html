02 · CONFIGURATION

建立任务进入 WCS 后所需的业务配置

用于建立 WCS 的业务类型、流程、筛选、调度和消息规则。通常由实施人员或具备配置权限的管理员维护。

CONFIGURATION · C1

Action Type Config

统一定义 WCS 可以接收和处理的业务作业类型。

WMS 下发入库、出库、盘点或容器搬运任务后，WCS 会根据 Action Type 识别业务类型，并匹配相应的流程和调度规则。管理员可在此集中维护各类作业类型，确保任务进入 WCS 后能够被正确识别和处理。

核心场景 · 新增整箱出库业务

让 WCS 先识别这是一项整箱出库任务

仓库准备上线整箱出库时，管理员先建立 CASE_OUTBOUND，并定义 WMS 下发任务需要携带的容器、工作站等业务数据。完成后，WCS 才能识别这类任务，并将其交给后续流程和调度配置处理。

新增业务类型→定义任务数据→供流程与调度引用
页面预览

从列表确认和维护作业类型

列表集中显示作业类型的编码、名称、说明、状态和创建时间，便于管理员快速确认当前配置；右侧 Operations 可进行编辑、停用或删除。

页面预览

创建新的作业类型

除基础信息外，还需根据业务需要配置入参校验、搜索字段、索引映射和取消任务规则。

新增或维护作业类型

Basic Info填写必填的 Code、Name，并通过 Description 说明适用业务。
Input Constraint Fields定义 WMS 下发该类 Job 时必须包含的扩展字段。系统在创建 Job 时校验并保存配置快照，后续修改不影响已有 Job。
Search Fields决定 Job Management 可以使用哪些业务字段查询任务。
Indexed Field Mapping将常用扩展字段映射为资源、工作站或业务分类索引，提高 Job 查询效率。

取消任务时的处理规则

Protect completed actions开启后，已完成的 WMS Action 不允许取消，避免误撤销已经结束的业务。
Cancel execution resources开启后，取消 Job 时同步清理相关 Command、Station Task 和 Node Execution。
Release action reservation开启后，取消 Job 时通知 WMS 释放该 Action 预留的库存或业务资源。

Action Type 创建后，任务还不能直接执行

还需要依次完成以下配置，任务才能被正确匹配、调度并进入执行流程。

Action Type定义任务类型→ Published Workflow定义执行步骤→ Job Filter匹配适用任务→ Scheduling Rule控制任务调度
如需向外部系统回传处理结果，再补充 Message Config。
CONFIGURATION · C2

Workflow Definitions

维护任务执行所采用的标准流程模板。

Action Type 说明“这是什么任务”，Workflow Definition 则规定“这项任务要按什么步骤完成”。例如一项收货任务可以依次经过检查收货位、呼叫 RCS 搬运、工作站确认、推荐上架位和完成入库；管理员可在流程设计器中把这些业务步骤组织成可执行的标准流程。

核心场景 · 标准收货流程

把收货作业拆成系统可以依次执行的步骤

货物到达后，系统先检查收货位并呼叫 RCS 将容器送到收货工位；操作员完成收货确认后，系统推荐上架位，再由 RCS 搬运入库并结束任务。管理员通过 Workflow Definition 固化这条标准路径。

检查收货位→搬到工作站→收货确认→推荐上架位→搬运入库
Action Type识别任务属于哪类业务例如收货、出库、盘点或容器搬运
→
Workflow Definition规定这类任务如何执行定义步骤顺序、判断条件、设备动作和结束方式
→
Published Workflow供调度规则正式引用任务匹配后按照已发布流程进入现场执行
页面预览

从列表查找并管理流程定义

列表显示流程名称、唯一 Process Key、当前状态和最后更新时间。管理员可查看历史版本、进入编辑，或通过更多操作调整流程状态。

页面预览

在 Process Designer 中组织完整业务路径

左侧提供系统预置的设备资源和流程控制节点。管理员可将需要的节点直接拖入画布，再连接步骤、设置分支并配置节点属性，从而组合或调整新的业务流程。

01选择节点从左侧组件库选择流程所需的设备、工作站、控制或事件节点。
02拖入画布将节点拖到中间画布，并按照实际业务顺序连接各步骤和条件分支。
03设置属性选中节点后，在属性面板中配置执行动作及输入、输出数据。
WCS Device Resources系统已支持的现场硬件或作业能力，例如 RCS Client、Equipment Control、Pick-to-Light、Traffic Light、Station 和 Accept Task。
WCS Flow Control用于控制流程走向和等待条件，例如 Decision、Wait、Service Task、Signal Wait 和 Conditional Wait。
Events / BPMN Components用于定义流程如何开始、结束、分支、捕获异常或进入子流程。
节点配置

选中节点，定义这一步具体执行什么

点击画布中的节点后，右侧会打开对应的属性面板。不同节点显示的配置项会有所不同，用于把业务步骤转换为系统可以执行的动作。

Node Name / Description说明该节点在业务流程中承担的步骤，名称应让后续维护人员能够直接理解。
Service Method指定该节点需要调用的系统能力。示例中的 completeJob 表示流程运行到这里时执行完成 Job 的动作。
Input Mapping把流程上下文中的数据传给当前节点，例如将当前 Job ID 提供给完成任务的方法。
Output Mapping将节点执行结果写回流程上下文，供后续判断或其他节点继续使用。
配置提示流程图负责描述步骤关系，节点属性决定每一步如何执行。新增节点后必须完成必要属性和数据映射，并在发布前检查各分支是否都能到达正确的结束节点。

流程从设计到停用的状态变化

只有 Published 状态的流程可以被新 Job 引用。状态调整只决定后续任务能否继续选用该流程，不会改变已经启动的 Workflow Instance。

Draft流程处于设计或修改阶段，不能被新 Job 引用。Publish →
Published流程已经发布，可以被 Job Filter 和后续调度配置引用。Deprecate →
Deprecated流程已停止供新 Job 使用，但既有实例仍按原版本继续执行。Archive →
Archived流程完成归档，不再继续流转。

Revert to Draft：Published 流程可退回 Draft 继续修改；完成调整后需要重新发布，才能再次供新任务引用。

修改流程为什么不会影响在途任务

每次发布都会保存一个流程版本快照，已经启动的 Workflow Instance 绑定其启动时的版本。因此编辑、重新发布、停用或退回草稿都不会改变正在执行的实例，只影响后续新任务。

History查看流程的创建、更新、发布、退回草稿、停用和归档记录，用于追溯版本变化。
Save As以当前流程为基础复制一份新定义，适合新流程与现有流程大部分步骤相同的场景。
Import从 BPMN 文件导入流程，适合迁移或复用已经准备好的流程定义。
Export导出流程及其相关配置，用于备份、评审或迁移到其他环境。
字段说明列表中的 Appendable 当前未发现对应的后端配置规则，应视为预留或已停用字段，不建议据此判断流程是否支持追加任务。
Restartable开启后，如果 Workflow Instance 因工作站会话超时（SESSION_TIMEOUT）终止，系统可以自动重新启动该流程；它不是普通失败后的通用重试开关。
CONFIGURATION · C3

System Workflows

让系统事件或现场操作自动启动指定的业务流程。

Workflow Definitions 负责设计“流程怎么执行”，System Workflows 则决定“什么情况下自动启动这条流程”。管理员为系统内置 Trigger 选择一个已发布的 Workflow Definition 并启用后，条件满足时 WCS 会自动创建相应的流程实例，无需人工逐次启动。

核心场景 · 拣货墙自动补货

让补货流程在需要时自动启动

拣货墙进入 SHIPPING 或 SHELVING 后，系统每 60 秒检查槽位库存。发现需要补货时，PW_REPLENISHMENT 自动启动已绑定的补货流程并请求 RCS 搬运容器，不需要管理员或操作员逐次创建任务。

拣货墙进入作业→检测到补货需求→自动启动补货流程

系统工作流如何启动

01 · Trigger触发条件满足系统检测到已配置的业务条件，或接收到操作员发起的指定操作
→
02 · Workflow Binding读取绑定的流程定义系统根据 Trigger 找到当前启用的 Published Workflow
→
03 · Workflow Instance创建并运行流程实例新实例按照启动时绑定的流程版本执行
页面预览

为系统 Trigger 选择并启用执行流程

列表直接展示触发器、业务说明、绑定的 Workflow Definition 和启用状态。下拉框只提供 Published 流程；Enabled 打开后，后续满足条件的事件才会启动所选流程。

后台自动运行的拣货墙流程

PW_REPLENISHMENT拣货墙进入 SHIPPING 或 SHELVING 后，每 60 秒检查槽位是否需要补货；有需求时自动请求 RCS 搬运补货容器。
PW_TASK_DECISION拣货墙进入 SHIPPING 后，每 5 秒检查任务，将处于 DECISION_ON 的任务推进为 IN_PROGRESS，交由操作员继续执行。
BUFFER_RETURN拣货墙进入 SHIPPING 后，每 5 秒检查缓存区利用率；低于设定阈值时，自动安排容器返回存储区。

由操作员主动发起的呼出流程

CONTAINER_CALL_OUT操作员在工作站输入容器条码并发起呼出后，系统启动容器呼出流程，将指定容器送往工作站。
ITEM_CALL_OUT操作员按商品维度发起呼出后，系统启动商品呼出流程，将存放该商品的容器送往工作站。

启停或更换流程时会发生什么

关闭 Enabled新的事件不再启动该流程；已经启动的 Workflow Instance 继续执行。
开启 Enabled后续事件满足 Trigger 条件时，系统按照当前绑定的 Published Workflow 启动新实例。
更换 Workflow新触发的流程使用更新后的 Workflow Definition；已启动实例继续使用启动时的版本快照。
退出活跃状态拣货墙从 SHIPPING / SHELVING 切换到 IDLE 或 LOCKED 时，系统终止该工作站相关的 System Workflow。
配置提示Workflow Definition 下拉框只显示 Published 流程。修改绑定后需确认配置已经成功提交并刷新页面核对；仅在下拉框中选择但未成功保存，不会改变实际触发关系。
CONFIGURATION · C4

Job Filters

通过业务条件筛选需要进入特定调度规则的任务。

WMS 下发 Job 后，WCS 会依次检查当前启用的 Job Filter，找到第一条满足条件的规则。Job Scheduling Rule 再根据匹配到的 Filter，为任务选择相应的 Workflow Definition 和调度策略。通过这种方式，同一套 WCS 可以让不同类型或属性的任务走不同的执行路径。

核心场景 · 按业务条件分流任务

让不同任务进入适用的执行策略

当 WMS 下发的 Job 中 actionType = TOTE_OUTBOUND 时，示例 Filter 匹配成功。后续 Job Scheduling Rule 根据这条 Filter，将任务交给周转箱出库所使用的 Workflow Definition。

Job 进入 WCS→Filter 匹配 actionType→进入出库调度策略
01 · Job Data读取 Job 的业务字段例如 actionType、优先级或 extensionData 中的自定义字段
→
02 · Job Filter判断是否满足全部条件启用的 Filter 按顺序匹配，找到第一条符合规则的配置
→
03 · Scheduling Rule选择执行流程和调度方式通过 jobFilterIds 关联 Filter，并指向相应 Workflow Definition
页面预览

查看和维护现有筛选规则

列表集中显示 Filter 的编码、名称、条件数量、启用状态和创建时间。管理员可按名称或状态查询，并根据业务变化新建、编辑、停用或删除规则。

配置示例

用“字段 + 运算符 + 表达式”建立匹配条件

示例条件为 actionType EQUALS TOTE_OUTBOUND，表示只匹配周转箱出库 Job。需要进一步限定任务时，可通过 Add Condition 增加其他判断。

一条条件由三部分组成

Field选择要判断的数据既可使用 actionType 等标准字段，也可使用 extensionData.skuCode 等自定义扩展字段。
Operator选择比较方式可进行等于、不等于、数值比较、列表匹配、文本包含、正则匹配或空值判断。
Expression填写期望匹配的值支持固定值、数组和相对时间表达式，例如 PUTAWAY、[A,B,C] 或 now()-1h。
多条件规则同一 Filter 中的多个 Match Conditions 使用 AND 逻辑，只有全部条件都满足时才算匹配。页面显示最多可添加 20 条条件，但当前代码和数据未确认存在后端硬性上限。

常用匹配方式

精确与列表EQUALS、NOT_EQUALS、IN、NOT_IN
数值比较GREATER_THAN、LESS_THAN、LESS_THAN_OR_EQUALS
文本判断CONTAINS、STARTS_WITH、ENDS_WITH、MATCHES
空值判断IS_NULL、IS_NOT_NULL

当字段不存在时，只有 IS_NULL 会匹配成功；IS_NOT_NULL 及其他比较方式均不会匹配。

配置顺序Job Filter 只负责识别“哪些 Job 属于这一组”，不会单独启动流程。创建后还需要在 Job Dispatch Settings 中引用该 Filter，并选择要执行的 Workflow Definition。
CONFIGURATION · C5

Job Dispatch Settings

决定符合条件的任务如何分组、等待并进入执行流程。

Job Filter 先识别“哪些 Job 适用”，Job Dispatch Settings 再决定这些 Job 使用哪条 Workflow、如何组成一批，以及何时开始执行。管理员通常在新增业务类型、调整作业节奏或控制单个流程承载量时维护这里的规则。

核心场景 · 将符合条件的任务分组调度

兼顾凑批效率与现场等待时间

例如将同一容器的 Job 归为一组，设置“满 3 个立即启动、最长等待 60 秒”。任务数量先达到 3 个时立即执行；不足 3 个但已经等待 60 秒时也会启动，避免现场为了凑批持续等待。

Filter 匹配 Job→按业务字段分组→批量或等待条件满足→追加或新建实例→Workflow 开始执行
页面预览

集中查看当前生效的调度策略

列表将 Job Filter、Workflow、批次条件和 Auto Schedule 状态放在同一行，便于管理员确认某类任务会进入哪条流程，并通过 Preview 在实际触发前检查待调度结果。

规则配置

确定任务范围、执行流程与成组方式

先选择适用的 Job Filter 和 Workflow，再根据业务是否需要合单设置 Grouping Attributes、批次条件与单个流程的最大任务数。截图中的规则按 ACTION_TYPE 分组，每个 Job 单独触发一次流程。

一条调度规则需要回答四个业务问题

哪些任务适用？Associated Filters 可关联一个或多个 Job Filter。多个 Filter 采用 OR 逻辑，Job 满足其中任意一条即可进入本规则。
进入哪条流程？Workflow 指定匹配任务后续执行的流程定义。应选择与业务类型和现场能力相符的已发布流程。
哪些任务合为一组？Grouping Attributes 按字段值组合分组，值相同的 Job 共用一个 Workflow Instance；不配置时默认按 actionType 分组。
什么时候开始执行？Min Jobs 与 Max Wait 采用 OR 逻辑：达到最低任务数立即启动，或等待达到上限时启动，不要求两个条件同时满足。

分组字段：可使用 containerCode、stationCode、actionType，也支持 extensionData.businessMode 等嵌套路径。字段在 Job 中不存在时按 null 处理，因此缺少相同字段值的 Job 可能被归入同一组。

任务是追加到现有流程，还是新建流程

APPEND追加到运行中的实例存在相同分组键的运行中 Workflow Instance，且当前 Job 数尚未达到 Max Jobs 时，新 Job 加入该实例继续执行。
CREATE_NEW创建新的流程实例没有可追加的同组实例，或现有实例已达到 Max Jobs 时，系统为这批 Job 创建新的 Workflow Instance。
Auto Schedule启用后，系统会自动检查并调度符合规则的 NEW Job；关闭后规则不会被定时调度器执行，但仍可通过 Preview 后的 Confirm Trigger 手动触发一次调度。
调度预览

先试算，再决定是否真正触发

Preview 只读取当前 NEW Job 并展示匹配数量与分组结果，不会创建流程或改变 Job 状态。截图中 Matched Jobs 和 Groups 均为 0，因此没有可触发的任务，Confirm Trigger 按钮处于不可用状态。

Total Pending Jobs当前等待调度的 NEW Job 总数，用于判断系统中是否存在待处理任务。
Matched Jobs / Groups本规则实际匹配到的任务数和分组数，用于核对 Filter 与 Grouping Attributes 是否符合预期。
Action有结果时，每组会显示 APPEND 或 CREATE_NEW，说明任务将追加到现有实例还是新建流程。
Confirm Trigger确认后才执行真实调度：创建或追加 Workflow Instance，并将对应 Job 从 NEW 更新为 SCHEDULED。
操作前确认Preview 可以反复检查且不会改变业务数据；Confirm Trigger 会立即执行调度。若预览结果与预期不符，应先取消并检查 Filter、分组字段、批次条件和 Workflow 选择。
CONFIGURATION · C6

Message Config

配置 WCS 向外部系统发送业务消息的方式。

当 Job 完成、失败或取消时，WCS 可以通过 HTTP 回调将处理结果通知 WMS 等外部系统。管理员在这里指定哪些 Job 事件需要通知、由哪个系统接收、发送什么内容，以及回调失败时如何重试。

核心场景 · 将异常结果及时回传上游系统

Job 失败后自动通知 WMS

当符合指定 Filter 的 Job 进入失败状态，WCS 使用 JOB_FAILED 配置生成回调地址、请求头和消息内容，并向 WMS 发送通知。如果网络暂时不可用，系统按设定间隔自动重试，避免现场异常只停留在 WCS 内部。

Job 状态变化→事件与 Filter 匹配→生成回调内容→HTTP POST 通知→失败时自动重试
页面预览

查看各类 Job 事件的回调配置

列表展示 Message Type、Subscriber、Callback URL、模板、发送方式、重试次数和关联的 Job Filter。管理员可据此确认某类任务在状态变化后会通知哪个外部系统。

哪些 Job 状态会触发消息

JOB_COMPLETEDJob 正常完成向外部系统回传作业已经成功结束。
JOB_FAILEDJob 执行失败向外部系统回传失败结果，便于及时处理异常。
JOB_CANCELLEDJob 被取消通知外部系统停止继续等待该任务结果。
Job Filter选择 Filter 后，只有满足该 Filter 的 Job 才会触发本配置；不选择时，该 Message Type 下的所有 Job 都会发送回调。若不同业务需要发送到不同地址，应分别建立 Filter 和 Message Config。
配置示例

定义接收方、地址与消息内容

示例在 Job 失败时向 WMS_LITE_TRIGGER 发送回调，并通过 Job Filter 仅处理指定业务。Callback URL、Headers 和 Payload Template 中的占位符会在发送时替换为当前 Job 的实际数据。

回调内容由四部分组成

Subscriber标识消息接收方，便于同一事件为不同外部系统维护各自的回调配置。
Callback URL指定接收地址，可使用 ${job.wmsActionId} 等占位符，将 Job 数据动态写入路径。
Headers以 JSON 配置请求头，可动态带入 Tenant、Facility 和时区等调用上下文。
Payload Template定义 HTTP POST 的 JSON 请求体，可引用 ${job.xxx} 和 ${extensionData.xxx} 等业务字段。

发送格式：系统使用 HTTP POST 发送回调，Content-Type 为 application/json。配置前应与接收方确认 URL、请求头、字段名称和占位符数据均符合双方接口约定。

03 · RUNTIME

追踪任务进入 WCS 后的实际执行状态

用于查看已经进入 WCS 的真实任务、流程和节点。问题排查通常从 Job Management 开始，再逐层下钻。

RUNTIME · R1

Job Management

集中查看和管理 WCS 接收到的业务任务。

每个 Job 对应 WMS 下发的一项业务任务。管理人员可通过 WMS Action ID、Action Type 或状态快速定位任务，确认它是否已经进入 WCS、是否开始执行，以及出现异常后应从哪里继续排查。

核心场景 · 排查任务为什么还未开始执行

从 NEW Job 追踪到调度规则

当 WMS 已下发任务，但现场迟迟没有收到作业时，先在 Job Management 根据 WMS Action ID 查询。若 Job 仍为 NEW 且 Workflow Instance 为空，说明任务尚未进入执行流程，需要继续检查 Action Type 对应的调度规则、自动调度状态及凑批条件。

查询 WMS Action ID→确认 Job 状态→查看 Workflow Instance→检查调度条件→确认等待原因

查询任务并判断当前处理阶段

列表将 WMS Action、Action Type、状态、优先级和关联 Workflow Instance 集中展示。截图中的任务均为 NEW，且尚未生成 Workflow Instance，表示它们仍在等待调度。

按三个阶段理解 Job 状态

等待执行NEWWMS 任务已经进入 WCS，正在等待符合条件的 Scheduling Rule 调度。
执行过程IN_PROGRESS · ON_HOLD · EXCEPTION任务正在执行、被业务流程暂停，或遇到仍有机会恢复的异常。
处理结束COMPLETED · CLOSED · FAILED · CANCELLED任务已正常结束、执行失败或被取消，不再按普通在途任务继续处理。

正常结束状态：系统数据中同时存在 COMPLETED 和 CLOSED，两者都表示任务已经正常结束；具体使用哪一种由对应业务流程决定。

任务详情

这些信息分别用来解决什么问题

任务是否正确进入 WCS？通过 WMS Action ID 和 Original Request 核对上游原始任务。
任务进入了哪条执行流程？结合 Action Type 和 Workflow Instance 判断调度去向，并继续追踪实际流程。
任务发生过哪些变化？通过 Operation Log 查看状态变化、操作人、来源和时间，还原处理过程。

列表中可用的管理操作

Adjust Priority仅用于 NEW Job。需要插单或调整等待顺序时修改优先级，新的数值会影响后续调度顺序。
Cancel用于 NEW、IN_PROGRESS、ON_HOLD 或 EXCEPTION Job。确认任务不应继续后取消，状态变为 CANCELLED。
异常排查Job 进入 EXCEPTION 或 FAILED 时，先查看异常信息和 Result Data，再通过 Workflow Instance 进入流程详情；需要定位具体失败步骤时，继续前往 Node Executions。
RUNTIME · R2

Workflow Instances

查看每次实际启动的流程当前运行到哪里。

Workflow Definition 是执行模板，Workflow Instance 是一批真实 Job 启动后的运行记录。管理人员可从这里确认哪些 Job 被组织在同一流程中、流程当前执行到哪里，以及出现异常后应检查哪个节点。

核心场景 · 判断运行中的流程是否停滞

从实例状态下钻到实际执行路径

当 Workflow Instance 长时间保持 RUNNING 时，先核对持续时间和 Related Jobs，再查看 Node Execution Records 与 View Flow。即使 Current Node 显示为空，也不能直接判定流程停滞，需要结合节点记录确认是否仍在异步执行或处于节点切换过程。

查询 Instance→核对 Related Jobs→检查持续时间→查看执行路径→定位异常节点
页面预览

快速筛选并判断流程运行状态

可通过 Instance ID、Definition ID、Status 或 Aggregation Key 查询。列表中的 Current Node 用于提示当前活跃步骤；运行中的实例会显示 Terminate 操作。

终止运行中实例列表中的 Terminate 仅用于确认不应继续运行的实例。执行后，实例变为 TERMINATED，关联 Job 自动变为 CANCELLED，同时取消子资源并释放流程预留资源。

按运行阶段理解实例状态

尚未执行CREATED流程实例已经创建，等待开始运行。
执行过程RUNNING流程正在执行，可能包含一个或多个关联 Job。
处理结束COMPLETED · FAILED · CANCELLED · TERMINATED流程已正常完成、失败、取消或被管理员主动终止。
实例详情

在同一页面核对任务、流程与节点

Related Jobs 说明本次流程包含哪些业务任务；Basic Info 用于确认流程定义、分组键和运行时长；Node Execution Records 展示每个步骤的状态、耗时、重试次数和错误信息。

哪些 Job 共用这次流程？Related Jobs 列出关联任务。相同 Aggregation Key 的 Job 可按照调度规则归入同一个 Workflow Instance。
流程现在执行到哪里？Current Node 记录当前活跃节点；Node Execution Records 则保留已经执行过的节点、持续时间和结果。
哪个步骤出现问题？通过节点状态、Retry 次数和 Error Message 定位异常；需要更完整的节点信息时，可继续进入 Node Executions。

Current Node 显示 “-”：不要直接判断为流程停滞。流程可能刚启动、正在切换节点或异步执行，应结合 Started At、运行时长和 Node Execution Records 判断。

执行路径

用流程图查看实际经过的节点

点击 View Flow 后，系统在流程定义上标出本次实例的实际执行路径。高亮节点表示已经执行或进入的步骤，淡化部分表示未进入的分支；Export Image 可将路径图导出用于问题沟通和留档。

运行中实例

向等待外部事件的流程发送 Signal

Signal Name 不是固定选项，而是由 Workflow Definition 中的 Signal Wait 节点决定。名称匹配时，等待该信号的节点继续执行；流程没有对应订阅时，发送操作不会推进流程。

适用场景唤醒等待外部事件的流程节点，或触发流程中预先设计的退出、补偿子流程。
操作要求必须使用流程配置中准确的 Signal Name。无法确认名称时，应先联系流程配置人员，不应反复尝试。
RUNTIME · R3

Node Executions

下钻查看流程中每个节点的执行结果。

Workflow Instance 用于判断整条流程的运行情况，Node Executions 则将流程拆解到每一个执行步骤。管理人员可按 Workflow Instance ID、Node ID 或 Status 查询，定位具体节点的状态、耗时、重试记录和错误原因。

核心场景 · 定位流程中的设备指令异常

从异常节点继续追踪关联 Command

当 RCS_CLIENT 或 EQUIPMENT 节点长时间未完成时，先查看节点状态和执行时间，再展开该行核对关联 Command。截图中的 rcs_return 节点已取消，而其 RCS_TASK Command 显示 TIMEOUT，说明排查重点应转向 RCS 指令和设备回调。

查询流程实例→找到异常节点→确认 Node Type→展开关联记录→检查设备或业务服务
页面预览

查看节点结果并展开关联执行记录

列表展示节点类型、状态、Retry、开始和完成时间及 Error Message。带“+”的记录可展开查看对应的 Command 等下游执行信息，从流程节点继续定位到设备或外部服务。

节点执行到什么状态？Status 区分等待、运行、完成、失败、超时、跳过或取消；Started At 与 Completed At 用于判断执行时长。
系统是否已经尝试重试？Retry 以“已重试次数 / 最大次数”显示，例如 0/3 表示尚未重试、最多允许 3 次；0/0 表示节点不允许重试。
失败原因是什么？Error Message 显示直接错误信息；需要核对节点收到和产生的数据时，再查看 Input / Output Variables 与节点配置快照。

根据 Node Type 选择后续排查方向

DECISION检查 Input Variables，确认进入该流程分支的判断依据是否正确。
SIGNAL_WAIT确认流程正在等待哪个 Signal，以及对应的外部事件是否已经发生。
SERVICE_TASK检查节点配置、输入输出和所调用的业务服务是否正常。
EQUIPMENT / RCS_CLIENT展开关联 Command，继续检查设备指令状态、目标设备和回调结果。
STATION继续检查工作站任务是否已创建、领取或完成，以及工作站会话是否正常。
ACCEPT检查任务是否仍在等待接手，以及是否存在符合能力条件的工作站。
判断失败速度若 Started At 与 Completed At 几乎相同，通常表示节点在校验配置或输入时立即失败；若间隔较长，则应优先检查等待的外部服务、设备回调或超时条件。
04 · ENTER STATION

确认作业地点

先查找并选中本次作业要使用的工作站，再点击 Confirm 进入工作站。

站点状态帮助操作员判断当前是否可用；确认后，后续作业都会在该工作站下执行。

05 · WORKSTATION

从统一入口进入各类现场作业

操作员登录工作站后，可根据当前要处理的业务选择出库、入库或库存作业。系统只显示该工作站能够承接的入口，避免操作员进入不适用的流程。

Back to Admin 返回 WCS 管理页面，用于查看配置或管理信息，不结束当前工作站登录。
Logout 结束当前工作站会话并返回工作站选择页；未完成任务会按系统规则取消或退回待领取池。

完成订单从拣选到待发运的处理

根据仓库采用的一体化、分段式或整箱出库流程选择对应入口。

Pick & Pack适用于单工位作业，操作员连续完成拣货、数量确认和打包，减少工序间交接。
Pick适用于拣货与打包分开的流程，按系统提示从库存中拣取商品并放入出库容器。
PACK适用于商品已完成拣选的场景，在独立打包工位完成包装和出库前确认。
Case Outbound适用于整箱商品直接出库，按箱确认出库数量和容器信息。
Pick To Wall适用于播种墙分拨，将已拣商品投入指定格口，按订单完成分单。
Picking Wall Pick适用于从播种墙格口取出已完成分单的商品，并转入打包或集货环节。
Outbound Staging适用于出库容器完成作业后，在发运前进入暂存区等待装车或交接。
Empty Tote Outbound适用于空周转箱退出作业区，将不再使用的空箱送往指定位置。
Outbound Container Addition适用于当前出库容器容量不足时，为订单追加容器以继续完成作业。

按到货形态完成收货与容器导入

根据到货商品是整箱、散件还是空周转箱，选择对应的接收方式。

Piece Receiving适用于散件到货，逐件扫描并确认实际收货数量。
Case Inbound适用于整箱到货，按箱核对商品和数量后完成入库接收。
Empty Tote Inbound适用于向作业区补充空周转箱，登记空箱进入工作站供后续任务使用。

处理盘点、容器整理和库存核对

用于确认账实一致，并在商品需要合并、拆分或转移时完成相应的库存操作。

Count适用于首次盘点，按任务核对库位、商品或托盘的实际数量并提交结果。
Recount适用于首次盘点存在差异的场景，由另一轮实盘再次确认差异是否真实存在。
Inventory Check适用于现场快速核对库存，查看容器或商品当前记录并与实物进行确认。
Picking Wall Count适用于播种墙盘点，核对各格口内商品，避免分单过程中的库存遗漏。
Consolidate适用于同类商品分散在多个容器中的场景，将库存合并到较少容器以释放空间。
Tote Split适用于一个周转箱需要拆分的场景，将部分商品转入其他容器并同步库存归属。
Container Transfer适用于更换容器或调整存放方式，将商品从源容器转移到目标容器。
STATION · S3

Accept Tasks

追踪候选任务是否已经被工作站和操作员接手。

Accept Tasks 是管理端的只读追踪页面。任务到达 Workflow 的 ACCEPT 节点后会进入符合能力条件的 Workstation Accept Pool；操作员在工作站接手后，管理人员可在这里确认接手结果。此页面不能执行 Accept、Cancel 或 Retry。

核心场景 · 确认任务为什么仍未进入工作站作业

从等待接手追踪到具体工作站

当 Job 已进入流程，但现场尚未开始处理时，可根据 Task ID 或 Business Type 查询 Accept Task。若状态为 Waiting for Acceptance，且 Station、Accepted By 和 Accepted Time 均为空，说明任务已经进入候选池，但还没有操作员在 Workstation 的 Accept Pool 接手。

流程到达 ACCEPT→进入候选池→能力匹配工作站→操作员接手→流程继续执行
页面预览

按任务或业务类型查询接手记录

列表将 Accept Task 与原始 Job、Action、商品或容器信息关联展示。`Read-only tracking` 表示该页面只用于管理追踪，实际接手操作仍在工作站进行。

任务详情

详情信息用来判断什么

任务是否仍在等待？Status 为 Waiting for Acceptance，表示任务已进入候选池但尚未接手。
任务将由哪些工作站处理？Required Capability 决定候选工作站范围；字段为空时，不按能力限制工作站。
任务最终由谁接手？接手后，Station、Accepted By 和 Accepted Time 会记录工作站、操作员和接手时间。
如何继续追踪流程？通过 Workflow Instance ID 查看整条流程，通过 Node Execution ID 定位 ACCEPT 节点记录。

Accept Task 的三种状态

WAITING_ACCEPT等待接手任务仍在候选池中，Station 与 Accepted By 尚未生成。
ACCEPTED已经接手任务已绑定工作站和操作员，Workflow 可以进入后续业务步骤。
CANCELLED已经取消ACCEPT 节点所在流程范围已被取消，任务不会继续等待接手。
取消后不会自动返回候选池被取消的 Accept Task 不会恢复为 WAITING_ACCEPT。若业务仍需重新派发，必须由上游流程创建新的 Accept Task，不能复用原记录。

当 WCS 内部任务已经完成，但 WMS 或其他订阅方没有收到状态更新时，应从 Message Send Logs 检查消息发送结果。

OPERATIONS · O1

Message Send Logs

追踪 WCS 向外部系统发送的每一条业务消息。

该页面用于辅助排查 WCS 向 WMS 等外部系统发送的业务消息。外部系统未收到任务结果时，可按 Job ID 查询记录，通过 Status、Retry 和 Fail Reason 判断消息是否发送失败；必要时由管理员查看详情并重新发送。
