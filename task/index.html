01
TASK · RECEIVE TASK

货车到仓后，逐步完成签到、卸货、收货的执行记录

Receive Task 由 Inbound Receipt 触发生成，代表一次完整的收货作业。它把"一辆车的货怎么卸下来、扫进系统"这个过程拆成步骤来管理。每个步骤完成后自动推进到下一步，全部完成后任务关闭。

核心场景

供应商送货到仓，操作员按步骤完成收货

一辆货车到达仓库，操作员先在系统签到（Dock Check In），确认月台占用；然后卸货（Offload），将货物从车上搬下；最后逐箱扫描建立容器（LP Setup），货物正式进入库存。

  1. Dock Check In货车到仓签到，确认月台（可跳过）
  2. Offload卸货，将商品从车上移至收货区（可跳过）
  3. LP Setup扫描建立 LP，商品正式进入系统库存（必须执行）

💡 可在 Customer Settings 中配置跳过 Dock Check In 和 Offload，任务创建时直接从 LP Setup 开始。

Receive Task · 列表

实时追踪每条收货任务的执行步骤与进度

Current Step 是日常巡检的关键字段。如果一批任务的 Current Step 长时间停在 Dock Check In，说明月台还没有人去签到；停在 Offload，说明卸货还没开始。Progress 显示已完成 LP 数 / 总数，让管理员不用逐条点开就能判断整体进度。

—

详情页

点击 Task ID 进入详情页，上方是任务的基本信息，下方按标签页查看执行情况。Steps 一开始就有；任务开始建立 LP 后会多出 LP Setup 标签。

—

Steps：看每个步骤走到哪里

每个步骤有独立的 Status 和 Action Progress，步骤按 Sequence 顺序排列。想知道一张任务卡在哪个动作，先看这里。

—

LP Setup：核对实际收了什么

记录这张任务实际建立的 LP，包括 LP 所在位置和 LP 类型，以及每个 SKU 的数量、批次和保质期。收货后对账或追溯某个 LP 的来源，从这里查。

02
TASK · PUT AWAY TASK

收货完成后，把货物搬到正确的存储库位

Put Away Task 负责将收货区的 LP 移入仓库存储区。系统根据 Put Away Strategies 自动推荐目标库位，操作员按任务指引搬运并扫码确认。任务完成后库存位置更新，并在满足库存状态及客户配置时进入可分配状态。

核心场景

货物建好 LP 后，还堆在收货区等待归位

收货区是货物入仓后的临时作业区域。LP Setup 完成后，系统根据 Put Away Strategies（上架策略）自动推荐目标库位并生成 Put Away Task。操作员按任务指引将 LP 搬运至目标库位扫码确认，库存位置随之更新；后续是否可用于出库分配，还取决于库存状态及客户配置。

  1. 系统推荐库位根据 Put Away Strategies 匹配最优目标库位
  2. 操作员搬运 LP按任务指示将容器移至目标位置
  3. 扫描入位确认扫描 LP 和库位，更新库存位置
Put Away Task · 列表

查看待上架任务及关联的收货来源

每条上架任务都能追溯到来源收货单和收货任务；Progress 反映已经归位的 LP 占比，可以用来判断这批货还剩多少没上架。
💡 生成时机由 Customer Settings 中的 Put Away Mode 控制：DURING_RECEIVING 每完成一个 LP 即生成；AFTER_RECEIVING 整个收货任务关闭后统一生成。

03
TASK · MOVEMENT TASK

库内任意位置之间的货物移动

Movement Task 用于在仓库内部将库存从一个位置移动到另一个位置，不涉及入库或出库流程。常见于库位整理、区域调整或临时移位等场景，由管理员手动创建。

典型场景

库内位置调整，不改变库存归属

Movement Task 只改变货物的物理位置，不触发入库或出库流程，也不改变库存业务状态。典型使用场景：库区规划调整、库位整理腾出整齐空间、拣货区手动补充（无 Min/Max 规则时）、设备维护临时移位等。

  1. 创建任务管理员指定来源库存与目标位置
  2. 执行搬运操作员确认 LP，将货物移动至目标位置
  3. 扫码确认扫描目标位置，库存位置更新
Movement Task · 列表

查看库内移动任务的执行状态

移库任务只负责改变货物的物理位置。想确认某次移位有没有执行完，在这里看任务状态即可；库存业务状态是否同时变化，以实际任务规则为准。

04
TASK · PICK TASK

出库订单分配到位后，指引操作员从库位取货

Pick Task 由 Order Dispatch 根据 Order Plan 的 Pick Method 和 Pick Mode 自动生成。它告诉操作员去哪个库位、取什么 SKU、取多少。拣货完成后，相关库存完成拣取并等待后续打包、合流或装车。

核心场景

出库高峰，多个订单同时等待拣货

Order Dispatch 将订单按 Pick Method 生成拣货任务后，Pick Task 列表里出现一批待执行任务。管理员在这里分配操作员（Assignee），操作员用手持设备（RF/PDA）按任务路线逐库位拣货。每条任务的 Progress 实时更新，管理员可以看到哪些任务在进行中、哪些已完成。

  1. Order Dispatch 生成任务按 Order Plan 的 Pick Method 和 Pick Mode 创建 Pick Task
  2. 分配操作员Batch Assign 批量指派，或逐条指派
  3. 手持端执行拣货操作员用 RF/PDA 按路线从库位取货
  4. 任务关闭库存状态变为 Picked，等待打包或装车
Pick Task · 列表

监控所有拣货任务的执行状态

列表关联 Order Plan ID 和 Order ID，可追溯拣货任务对应的订单和计划。Pick Method 和 Pick Mode 在任务创建时已确定，反映 Order Plan 的配置。

05
TASK · PACK TASK

将多个已拣货箱子合并到一个托盘，准备整托装车

本节说明 Pack Task 中的 CONSOLIDATE_PALLET 类型，适用于整车（TL）、零担（LTL）或自提（WILL_CALL）的发货场景。操作员将多个 CLP（箱子）扫描归入同一个 SLP（托盘），完成后托盘作为整体进入后续装车流程。

核心场景

整车发货前，把分散在库区的箱子合并到托盘上

整车发货时，同一个订单的货物可能分散在多个箱子（CLP）里。在装车前需要将这些箱子归拢到一个托盘（SLP）上，方便叉车一次性搬运。Pack Task 就是这个合托动作的执行记录。合托时系统会校验所有箱子必须属于同一客户、同一承运商、同一收货地址。

  1. 扫描 SLP确认目标托盘，系统校验托盘类型和状态
  2. 逐个扫描 CLP将箱子逐一扫入托盘，系统返回各箱关联的订单信息
  3. 提交确认一致性校验通过后，CLP 归入 SLP，相关订单状态更新为 PACKED
Pack Task · 列表

查看合托任务的执行状态

Pack Task 可由管理员在 PC 端手动创建（选择已 PICKED 状态的订单），也可在 Order Plan 配置 autoCreatePackTask 后由系统在拣货完成时自动创建。

TASK · CONSOLIDATE TASK

把分散在多个 Tote 的库存合并，腾出空容器

Consolidate Task 用于 AGV 自动化仓：把同一客户、库存状态为 OPEN 的库存集中到更少的 Tote，SKU 不要求相同。

核心场景

多个 Tote 只装了一点货，需要合并腾出空容器

AGV 自动化仓里，同一客户的库存常常散落在多个半空的 Tote 中，占着容器和库位。管理员在 Add 页面用筛选条件挑出这些半空 Tote，加入合并清单后创建任务，系统把货集中到更少的 Tote，空出来的容器可以循环使用。

  1. 查找 Tote筛出库存分散、填充率低的 Tote
  2. 加入合并清单勾选结果后点 Add to Consolidate Line
  3. 创建任务选择是否经过 ST（工作站）
  4. 跟踪进度在详情页查看来源 Tote 和步骤
Consolidate Task · 列表

合并任务的执行进展在这里跟踪

任务创建后，可以在这里查看每个合并任务是在等待、进行中还是已完成，由哪个站点和执行人处理。点击 Task ID 进入详情，查看来源 Tote 和合并过程。

—

创建合并任务

先用 Customer、SKU、Fill Rate (%)、SKU Count、Total Qty、Single Item Qty、Lot No 找出候选 Tote。Fill Rate 越低表示越空。
Consolidate Line
勾选搜索结果后加入清单，清单里可以移除不需要的 Tote。
Create Task
Create Task Without ST 与 Create Task With ST 二选一；Cancel 放弃创建。
—

详情页：来源 Tote 与步骤

点击 Task ID 进入详情页，顶部有 Back 和 Assign 按钮。

Basic Info
Task ID、状态、客户、目标库位、开始与结束时间、创建人。
Source Totes
列出参与合并的 Tote、所在库位和 LP ID，数量显示在标题里。
Steps
显示 CONSOLIDATE 步骤的状态和 Action Progress（已完成动作数 / 总数）。
Consolidate History
记录每次合并的明细，用来确认货搬到了哪个 Tote。

TASK · ASSEMBLY TASK

按 BOM 把组件装配成套件，再继续出库

Assembly Task 用在 Kitting 场景：组件装配完成后，套件作为一个整体继续出库。

核心场景

订单要的是套件，需要先把组件装配起来

出库订单里含有 Is Kitting 商品时，系统会生成 Assembly Task；管理员也可以在 Create 页面手动建一个。操作员按 BOM 取出各组件完成组装，完成后的套件继续走出库流程。只有配置了 Kitting 商品的客户才会用到。

Assembly Task · 列表

组装任务在这里指派和启动

行末三个图标依次是 Start（开始）、Delete（删除）、Assign（指派）。需要一次指派多条任务时，勾选后使用 Batch Assign。

—

手动创建套件任务

Customer
先选客户。未选客户时 Add Item 不能点。
Kit Items
点击 Add Item，在 Search kit item 中搜索套件商品并填写 Qty，Action 列可移除该行。
Submit
提交后生成 Assembly Task；Cancel 返回列表。

TASK · SORT TASK

把批量拣出的货按订单分拣

Sort Task 对应批量拣货之后的分拣步骤，用来查看分拣任务的批次、模式和状态。

核心场景

一批拣好的货要按订单分拣

批量拣货（Batch / Wave）把多个订单的货一起拣出来，之后需要按订单拆开。Sort Task 记录这一步，列表里能看到它来自哪个批次（Batch No）、哪个波次（Wave No）、关联哪条 Pick Task，以及按哪种模式（Manual、WCS Auto、Hybrid）分拣。

Sort Task · 列表

分拣任务按批次跟踪进度

每条分拣任务都关联到所属批次和拣货任务，用来跟踪这批订单的分拣进度。

TASK · PUT BACK TASK

将已拣货但未发运的库存退回可用存储区

Put Back Task 用于把已从库位取出、但因各种原因未能发运的库存归还原位或放入其他存储位置，使其重新进入可分配状态。

典型触发场景

拣货后订单取消，货物需要归还库位

拣货完成后，订单因客户取消或库存问题无法发运，已拣出的货物不能留在暂存区——Put Back Task 指引操作员将这些货物送回合适的存储位置，重新变为可用库存。

  1. 订单取消 / 超拣已拣货但订单被取消，或拣出数量超过需求
  2. 人工退库管理员手动发起，将指定 LP 退回存储区
  3. 未发运返库装车后因故未能发运，货物需要重新入库
Put Back Task · 列表

查看退库任务的执行状态

每条退库任务都对应一张订单。Put Back Type 为 MANUAL 表示由管理员手动创建；其他类型（订单取消、超拣）由系统自动触发。

—

详情页

点击 Task ID 进入详情页，包含三个标签页。

—

Basic Info：确认这张退库任务的来由

显示任务对应的订单、退库类型、状态和指派人。想知道为什么会产生这张任务，先看 Put Back Type。

—

Task Steps：确认执行到哪一步

显示 Put Back 步骤的状态和指派人。

—

Put Back History：确认货物退回到哪里

任务执行后，每件货物的退回记录会出现在这里，包括退回的 SKU、数量，以及从哪个 LP 和库位退到了哪个 LP 和库位。这是确认货物最终去向的最直接依据。

10
TASK · REPLENISHMENT TASK

将库存从储存区搬运到拣货区，保障拣货区不断货

Replenishment Task 由 Min/Max Setting 的 Scheduler 或手动 Trigger 触发生成。它指定从哪个来源位置（From VLG）取货、搬到哪个拣货位置（To VLG），通过 Collect → Drop 两步完成库存位置的实际移动。

核心场景

拣货区库存低于阈值，系统自动安排补货

当 Min/Max 规则检测到拣货区的某个 SKU 库存低于 Min Qty 时，系统自动创建 Replenishment Task。操作员按任务指示到储存区取出对应 LP，搬运到拣货区指定库位放下，任务完成，库存位置更新。

  1. Collect（取货）操作员到 From VLG 扫描取出来源库存
  2. Drop（放下）搬运到 To VLG 目标库位扫码确认入位
Replenishment Task · 列表

查看所有补货任务的执行状态

补货任务的 Source 说明它是怎么产生的，MANUAL 表示手动创建，方便排查为什么会出现这次补货；SKUs 是该任务涉及的商品数。具体的来源与目标库位在任务详情里查看。页面上方的 Scheduler Config 用于配置自动补货的调度，Execution Log 记录调度的执行情况，Add 可手动创建补货任务。

TASK · INVENTORY CHECK TASK

叫容器到工作站，核对实物与系统库存

Inventory Check Task 用来确认自动化仓里的实物是否与系统库存一致。

核心场景

怀疑某批库存与系统不符，叫容器到工作站核对

Inventory Check Task 适用于自动化仓：管理员在 Add 页面用筛选条件圈定要核对的库存，比如某个客户的商品、填充率偏低的容器，或很久没被拣过的容器。创建任务后，系统把对应容器呼叫到工作站，由人核对实物和系统库存是否一致。

Inventory Check Task · 列表

查看每个盘点核对任务的进展

每条记录对应一个需要核对的容器，Station 表示容器被呼叫到的工作站。状态变为完成后，说明该容器的实物与系统库存已核对完毕。

—

先查库存，再创建核对任务

Inventory Search
条件有 Customer、SKU、Location、Fill Rate（范围，单位 %）、Lot No、Tote ID、Recent Picking Time。其中 Customer 为必填，未选会提示 Customer is required。
Search / Reset
Search 查出符合条件的库存，Reset 清空条件。

TASK · LOAD TASK

将货物装上车，完成后触发发运记录生成

管理员先在 Load Management 创建 Load，再从对应 Load 创建装车任务。操作员执行装车扫描；满足关闭条件后由管理员关闭 Load Task，系统随之处理关联 Load，并生成 Shipment Ticket。

核心场景

承运商车辆到达月台，仓库需要确认这一车该装哪些货

当订单完成拣货、打包并被安排到某个 Load 后，装车现场需要核对车辆、Dock、Carrier 以及实际装入的 LP。Load Task 记录这次交接过程，确保货物不是“计划已发”，而是已经完成现场装车确认。

—

手持端 · 按步骤完成装车

手持端把装车现场拆成 Dock Check In、Loading、Sign BOL 三个检查点，方便操作员按实际交接进度推进。

Loading 阶段用于扫描并确认货物装入对应 Load；Sign BOL 用于完成装车后的单据确认。

Load Task · 列表

查看装车任务及关联 Load 信息

每条装车任务对应一个或多个 Load，Current Step 和 Progress 显示现场装车进行到哪一步。Detail 用于查看任务详情，Start 用于开始装车；装车完成后的关闭动作会触发后续发运记录处理。

TASK · TASK ACTION

任务执行动作的明细，排查状态与库存差异

Task Action 覆盖所有任务类型，主要用于排查任务状态异常和库存位置不一致。

核心场景

任务状态或库存位置不对，要回溯每一步动作

Task Action 是所有任务类型的动作明细。管理员遇到任务卡住、库存位置和预期不一致时，可以按 Task ID、Action ID 或 Task Type 找到对应动作，看它从哪个库位到哪个库位、数量多少、有没有发给 WCS，以及 WCS 的处理状态。

Task Action · 列表

每个具体动作是否成功交给 WCS，在这里确认

每条记录是任务拆出来的一个具体动作，Send To WCS 与 WCS Status 用来判断它有没有成功交给 WCS，Status 为 Failed 的动作需要优先排查。Task Type 覆盖收货、上架、拣货、盘点、装车等十类任务。表格较宽，需要左右滚动，下面分成左右两段展示。每行的 Detail 可查看动作详情。

入口列表上方的 WCS Send Records 按钮会跳到 WCS Send Log 页面。
14
TASK · WCS SEND LOG

系统发给 WCS 的每条指令及其结果

WCS Send Log 记录系统向 WCS 发送指令的成败，用于排查设备或接口通信问题。

核心场景

设备没有动，要确认指令有没有成功发给 WCS

系统每次向 WCS 发出指令都会留一条记录。设备不动或任务停在发送环节时，可以按 Action ID 或 Result 找到对应记录，看发送是否成功、WCS 返回的 Job ID 和 HTTP 状态；失败的记录可以用行末的 Retry 重新发送。

发送失败的记录在这里排查与重发

把 Result 筛选为 Failed，就能快速找到下发失败的记录。Result 是开关样式，开启表示成功。点行首箭头可展开本次发送的请求头与请求内容，结合 HTTP Status 和 WCS Job ID 判断 WCS 是否收到。Retry 会重新向 WCS 发送，请确认原因已处理后再点。

TASK · TASK ASSIGNMENT

用一张看板了解每位操作员的任务负载

Task Assignment 汇总各类任务在每位操作员手上的 NEW 与 IN PROG 数量，帮助管理员在派发任务前判断人力分布。

核心场景

高峰时段，管理员要看谁手上任务多、谁空闲

任务分配前，管理员常常需要先了解每位操作员当前手上有多少待办。Task Assignment 把所有操作员和各类任务放在同一张看板里，每个格子显示该操作员在这类任务上的 NEW（未开始）和 IN PROG（进行中）数量，方便把新任务派给手上较少的人。

  1. 看板一行一位操作员，一列一种任务
  2. 筛选任务类型点击顶部的任务类型按钮显示或隐藏对应列
  3. 找到空闲的人数字小的操作员更适合接新任务
  4. 回到列表指派到对应任务列表执行 Assign 或 Batch Assign
Task Assignment · 列表

看板显示每位操作员的任务负载

顶部可选择 Receive、Put Away、Pick、Movement、Replenishment、Pack、Put Back、Assembly、Cycle Count、Load 十类任务；点击按钮可隐藏或重新显示对应列，Refresh 重新读取数据。列表底部的 Unassigned 行统计还没有指派人的任务，便于优先处理。这个页面只用来查看，指派动作在各任务的列表里完成。
