Orbiflow-WCS
产品功能与操作说明

面向业务管理人员、现场操作员及实施运维人员，说明 Orbiflow-WCS 各页面的适用场景、关键操作与业务结果。

开始阅读
01 · DASHBOARD

Dashboard 用于查看现场运行概况

先看这里，判断系统今天有没有正常跑起来，再决定要去任务、告警、设备还是通信页面下钻。

任务总量

看今天有没有持续接收、完成和积压。

趋势变化

看某个时段是不是突然变慢或停住。

告警状态

看有没有需要优先处理的异常。

设备与通信

看问题更像业务卡点还是链路问题。

当前站点行为 WCS Dashboard 默认每 30 秒 Auto Refresh，可调整刷新间隔，也可点 Refresh data 手动刷新；Edit dashboard 可调整卡片布局。顶部为 Today Received、In Progress、Waiting、Exception、Cancelled 五张任务卡；其下有 Hourly Trend 与 Hourly Completed（均为最近 24 小时）、Alert Statistics（Pending Alerts、Today New、Critical Alerts）、Workflow status、Device communication（Comm Total、Comm Success、Comm Failed）、Device health（Device Instances、Healthy、Unhealthy），底部是可按 Action ID 或 Job Type、Status 筛选的 Recent Jobs。各卡片均显示最近更新时间；“实时”应理解为按刷新设置更新，而不是无间隔推送。
02 · CONFIGURATION

建立任务进入 WCS 后所需的业务配置

用于建立 WCS 的业务类型、流程、筛选、调度和消息规则。通常由实施人员或具备配置权限的管理员维护。

CONFIGURATION · C1

Job Type Config

统一定义 WCS 可以接收和处理的业务作业类型。

WMS 下发入库、出库、盘点或容器搬运任务后，WCS 会根据 Job Type 识别业务类型，并匹配相应的流程和调度规则。管理员可在此集中维护各类作业类型，确保任务进入 WCS 后能够被正确识别和处理。

核心场景 · 新增整箱出库业务

让 WCS 先识别这是一项整箱出库任务

仓库准备上线整箱出库时，管理员先建立 CASE_OUTBOUND，并定义 WMS 下发任务需要携带的容器、工作站等业务数据。完成后，WCS 才能识别这类任务，并将其交给后续流程和调度配置处理。

新增业务类型→定义任务数据→供流程与调度引用
页面预览

从列表确认和维护作业类型

列表集中显示作业类型的编码、名称、说明、状态和创建时间，便于管理员快速确认当前配置；右侧 Operations 可进行编辑、停用或删除。

页面预览

创建新的作业类型

除基础信息外，还需根据业务需要配置入参校验、搜索字段、索引映射和取消任务规则。

新增或维护作业类型

Basic Info填写必填的 Code、Name，并通过 Description 说明适用业务。
Input Constraint Fields定义 WMS 下发该类 Job 时必须包含的扩展字段。系统在创建 Job 时校验并保存配置快照，后续修改不影响已有 Job。
Search Fields决定 Job Management 可以使用哪些业务字段查询任务。
Indexed Field Mapping将常用扩展字段映射为资源、工作站或业务分类索引，提高 Job 查询效率。

取消任务时的处理规则

Protect completed actions开启后，已完成的 WMS Action 不允许取消，避免误撤销已经结束的业务。
Cancel execution resources开启后，取消 Job 时同步清理相关 Command、Station Task 和 Node Execution。
Release action reservation开启后，取消 Job 时通知 WMS 释放该 Action 预留的库存或业务资源。

Job Type 创建后，任务还不能直接执行

还需要依次完成以下配置，任务才能被正确匹配、调度并进入执行流程。

Job Type定义任务类型→ Published Workflow定义执行步骤→ Job Filter匹配适用任务→ Scheduling Rule控制任务调度
如需向外部系统回传处理结果，再补充 Message Config。
CONFIGURATION · C2

Workflow Definitions

维护任务执行所采用的标准流程模板。

Job Type 说明“这是什么任务”，Workflow Definition 则规定“这项任务要按什么步骤完成”。例如一项收货任务可以依次经过检查收货位、呼叫 RCS 搬运、工作站确认、推荐上架位和完成入库；管理员可在流程设计器中把这些业务步骤组织成可执行的标准流程。

核心场景 · 标准收货流程

把收货作业拆成系统可以依次执行的步骤

货物到达后，系统先检查收货位并呼叫 RCS 将容器送到收货工位；操作员完成收货确认后，系统推荐上架位，再由 RCS 搬运入库并结束任务。管理员通过 Workflow Definition 固化这条标准路径。

检查收货位→搬到工作站→收货确认→推荐上架位→搬运入库
Job Type识别任务属于哪类业务例如收货、出库、盘点或容器搬运
→
Workflow Definition规定这类任务如何执行定义步骤顺序、判断条件、设备动作和结束方式
→
Published Workflow供调度规则正式引用任务匹配后按照已发布流程进入现场执行
页面预览

从列表查找并管理流程定义

列表显示流程名称、唯一 Process Key、当前状态和最后更新时间。管理员可查看历史版本、进入编辑，或通过更多操作调整流程状态。

页面预览

在 Process Designer 中组织完整业务路径

左侧提供系统预置的设备资源和流程控制节点。管理员可将需要的节点直接拖入画布，再连接步骤、设置分支并配置节点属性，从而组合或调整新的业务流程。

01选择节点从左侧组件库选择流程所需的设备、工作站、控制或事件节点。
02拖入画布将节点拖到中间画布，并按照实际业务顺序连接各步骤和条件分支。
03设置属性选中节点后，在属性面板中配置执行动作及输入、输出数据。
WCS Device Resources系统已支持的现场硬件或作业能力，例如 RCS Client、Equipment Control、Pick-to-Light、Traffic Light、Station 和 Accept Task。
WCS Flow Control用于控制流程走向和等待条件，例如 Decision、Wait、Service Task、Signal Wait 和 Conditional Wait。
Events / BPMN Components用于定义流程如何开始、结束、分支、捕获异常或进入子流程。
节点配置

选中节点，定义这一步具体执行什么

点击画布中的节点后，右侧会打开对应的属性面板。不同节点显示的配置项会有所不同，用于把业务步骤转换为系统可以执行的动作。

Node Name / Description说明该节点在业务流程中承担的步骤，名称应让后续维护人员能够直接理解。
Service Method指定该节点需要调用的系统能力。示例中的 completeJob 表示流程运行到这里时执行完成 Job 的动作。
Input Mapping把流程上下文中的数据传给当前节点，例如将当前 Job ID 提供给完成任务的方法。
Output Mapping将节点执行结果写回流程上下文，供后续判断或其他节点继续使用。
配置提示流程图负责描述步骤关系，节点属性决定每一步如何执行。新增节点后必须完成必要属性和数据映射，并在发布前检查各分支是否都能到达正确的结束节点。

流程从设计到停用的状态变化

只有 Published 状态的流程可以被新 Job 引用。状态调整只决定后续任务能否继续选用该流程，不会改变已经启动的 Workflow Instance。

Draft流程处于设计或修改阶段，不能被新 Job 引用。Publish →
Published流程已经发布，可以被 Job Filter 和后续调度配置引用。Deprecate →
Deprecated流程已停止供新 Job 使用，但既有实例仍按原版本继续执行。Archive →
Archived流程完成归档，不再继续流转。

Revert to Draft：Published 流程可退回 Draft 继续修改；完成调整后需要重新发布，才能再次供新任务引用。

修改流程为什么不会影响在途任务

每次发布都会保存一个流程版本快照，已经启动的 Workflow Instance 绑定其启动时的版本。因此编辑、重新发布、停用或退回草稿都不会改变正在执行的实例，只影响后续新任务。

History查看流程的创建、更新、发布、退回草稿、停用和归档记录，用于追溯版本变化。
Save As以当前流程为基础复制一份新定义，适合新流程与现有流程大部分步骤相同的场景。
Import从 BPMN 文件导入流程，适合迁移或复用已经准备好的流程定义。
Export导出流程及其相关配置，用于备份、评审或迁移到其他环境。
字段说明列表中的 Appendable 当前未发现对应的后端配置规则，应视为预留或已停用字段，不建议据此判断流程是否支持追加任务。
Restartable开启后，如果 Workflow Instance 因工作站会话超时（SESSION_TIMEOUT）终止，系统可以自动重新启动该流程；它不是普通失败后的通用重试开关。
CONFIGURATION · C3

System Workflows

让系统事件或现场操作自动启动指定的业务流程。

Workflow Definitions 负责设计“流程怎么执行”，System Workflows 则决定“什么情况下自动启动这条流程”。管理员为系统内置 Trigger 选择一个已发布的 Workflow Definition 并启用后，条件满足时 WCS 会自动创建相应的流程实例，无需人工逐次启动。

核心场景 · 拣货墙自动补货

让补货流程在需要时自动启动

拣货墙进入 SHIPPING 或 SHELVING 后，系统每 60 秒检查槽位库存。发现需要补货时，PW_REPLENISHMENT 自动启动已绑定的补货流程并请求 RCS 搬运容器，不需要管理员或操作员逐次创建任务。

拣货墙进入作业→检测到补货需求→自动启动补货流程

系统工作流如何启动

01 · Trigger触发条件满足系统检测到已配置的业务条件，或接收到操作员发起的指定操作
→
02 · Workflow Binding读取绑定的流程定义系统根据 Trigger 找到当前启用的 Published Workflow
→
03 · Workflow Instance创建并运行流程实例新实例按照启动时绑定的流程版本执行
页面预览

为系统 Trigger 选择并启用执行流程

列表直接展示触发器、业务说明、绑定的 Workflow Definition 和启用状态。下拉框只提供 Published 流程；Enabled 打开后，后续满足条件的事件才会启动所选流程。

后台自动运行的拣货墙流程

PW_REPLENISHMENT拣货墙进入 SHIPPING 或 SHELVING 后，每 60 秒检查槽位是否需要补货；有需求时自动请求 RCS 搬运补货容器。
PW_TASK_DECISION拣货墙进入 SHIPPING 后，每 5 秒检查任务，将处于 DECISION_ON 的任务推进为 IN_PROGRESS，交由操作员继续执行。
BUFFER_RETURN拣货墙进入 SHIPPING 后，每 5 秒检查缓存区利用率；低于设定阈值时，自动安排容器返回存储区。

由操作员主动发起的呼出流程

CONTAINER_CALL_OUT操作员在工作站输入容器条码并发起呼出后，系统启动容器呼出流程，将指定容器送往工作站。
ITEM_CALL_OUT操作员按商品维度发起呼出后，系统启动商品呼出流程，将存放该商品的容器送往工作站。

启停或更换流程时会发生什么

关闭 Enabled新的事件不再启动该流程；已经启动的 Workflow Instance 继续执行。
开启 Enabled后续事件满足 Trigger 条件时，系统按照当前绑定的 Published Workflow 启动新实例。
更换 Workflow新触发的流程使用更新后的 Workflow Definition；已启动实例继续使用启动时的版本快照。
退出活跃状态拣货墙从 SHIPPING / SHELVING 切换到 IDLE 或 LOCKED 时，系统终止该工作站相关的 System Workflow。
配置提示Workflow Definition 下拉框只显示 Published 流程。修改绑定后需确认配置已经成功提交并刷新页面核对；仅在下拉框中选择但未成功保存，不会改变实际触发关系。
CONFIGURATION · C4

Capability Workflow Mappings

为工作站能力绑定对应的 Workflow Definition，并控制该能力是否启用。

Capability Workflow Mappings 以工作站能力为配置入口。管理员可以为每种 Capability 选择可执行的 Workflow Definition，并通过 Enabled 开关控制该绑定是否生效。当前页面同时提供 Reset 和 Save，用于放弃本行未保存的修改或提交绑定变更。

核心场景 · 让不同能力的工作站执行不同流程

先确认能力，再决定工作站采用哪条流程

当同一类任务需要根据工作站能力进入不同执行流程时，先在 Capability Workflow Mappings 中找到对应能力，再选择 Published Workflow Definition。保存后还要确认 Enabled 状态和页面刷新结果，避免只改变下拉框而没有提交配置。

选择 Capability→绑定 Workflow Definition→启用并保存
页面预览

按能力查看并调整流程绑定

页面以 Capability 为单位，显示它绑定的 Workflow Definition 和 Enabled 开关，并提供 Reset 与 Save。

页面上需要核对的信息

Capability工作站具备的作业能力，例如 PICK、CASE_INBOUND 或 INVENTORY_CHECK。
Workflow Definition该能力对应的流程定义；绑定前应确认流程已发布且适配现场作业。
Enabled控制当前能力绑定是否参与后续工作站流程匹配。
Reset / SaveReset 放弃当前行修改，Save 提交当前行配置；完成保存后应刷新页面复核。
与 Job Dispatch 的区别Job Dispatch Settings 负责按任务条件进行调度和分组；Capability Workflow Mappings 负责把工作站能力与流程定义对应起来。两者都正确时，任务才可能进入符合能力的工作站执行路径。
CONFIGURATION · C5

Job Filters

通过业务条件筛选需要进入特定调度规则的任务。

WMS 下发 Job 后，WCS 会依次检查当前启用的 Job Filter，找到第一条满足条件的规则。Job Scheduling Rule 再根据匹配到的 Filter，为任务选择相应的 Workflow Definition 和调度策略。通过这种方式，同一套 WCS 可以让不同类型或属性的任务走不同的执行路径。

核心场景 · 按业务条件分流任务

让不同任务进入适用的执行策略

当 WMS 下发的 Job 中 actionType = TOTE_OUTBOUND 时，示例 Filter 匹配成功。后续 Job Scheduling Rule 根据这条 Filter，将任务交给周转箱出库所使用的 Workflow Definition。

Job 进入 WCS→Filter 匹配 actionType→进入出库调度策略
01 · Job Data读取 Job 的业务字段例如 actionType、优先级或 extensionData 中的自定义字段
→
02 · Job Filter判断是否满足全部条件启用的 Filter 按顺序匹配，找到第一条符合规则的配置
→
03 · Scheduling Rule选择执行流程和调度方式通过 jobFilterIds 关联 Filter，并指向相应 Workflow Definition
页面预览

查看和维护现有筛选规则

列表集中显示 Filter 的编码、名称、条件数量、启用状态和创建时间。管理员可按名称或状态查询，并根据业务变化新建、编辑、停用或删除规则。

配置示例

用“字段 + 运算符 + 表达式”建立匹配条件

示例条件为 actionType EQUALS TOTE_OUTBOUND，表示只匹配周转箱出库 Job。需要进一步限定任务时，可通过 Add Condition 增加其他判断。

一条条件由三部分组成

Field选择要判断的数据既可使用 actionType 等标准字段，也可使用 extensionData.skuCode 等自定义扩展字段。
Operator选择比较方式可进行等于、不等于、数值比较、列表匹配、文本包含、正则匹配或空值判断。
Expression填写期望匹配的值支持固定值、数组和相对时间表达式，例如 PUTAWAY、[A,B,C] 或 now()-1h。
多条件规则同一 Filter 中的多个 Match Conditions 使用 AND 逻辑，只有全部条件都满足时才算匹配。页面标题栏会显示已添加条件数，例如 1/20，单个 Filter 最多可添加 20 条条件。编辑已有 Filter 时，Code 为只读；Name、Job Mode 和 Enabled 开关可调整。

常用匹配方式

精确与列表EQUALS、NOT_EQUALS、IN、NOT_IN
数值比较GREATER_THAN、LESS_THAN、LESS_THAN_OR_EQUALS
文本判断CONTAINS、STARTS_WITH、ENDS_WITH、MATCHES
空值判断IS_NULL、IS_NOT_NULL

当字段不存在时，只有 IS_NULL 会匹配成功；IS_NOT_NULL 及其他比较方式均不会匹配。

配置顺序Job Filter 只负责识别“哪些 Job 属于这一组”，不会单独启动流程。创建后还需要在 Job Dispatch Settings 中引用该 Filter，并选择要执行的 Workflow Definition。
CONFIGURATION · C6

Job Dispatch Settings

决定符合条件的任务如何分组、等待并进入执行流程。

Job Filter 先识别“哪些 Job 适用”，Job Dispatch Settings 再决定这些 Job 使用哪条 Workflow、如何组成一批，以及何时开始执行。管理员通常在新增业务类型、调整作业节奏或控制单个流程承载量时维护这里的规则。

核心场景 · 将符合条件的任务分组调度

兼顾凑批效率与现场等待时间

例如将同一容器的 Job 归为一组，设置“满 3 个立即启动、最长等待 60 秒”。任务数量先达到 3 个时立即执行；不足 3 个但已经等待 60 秒时也会启动，避免现场为了凑批持续等待。

Filter 匹配 Job→按业务字段分组→批量或等待条件满足→追加或新建实例→Workflow 开始执行
页面预览

集中查看当前生效的调度策略

列表将 Job Filter、Workflow、批次条件和 Auto Schedule 状态放在同一行，便于管理员确认某类任务会进入哪条流程，并通过 Preview 在实际触发前检查待调度结果。

规则配置

确定任务范围、执行流程与成组方式

先选择适用的 Job Filter 和 Workflow，再根据业务是否需要合单设置 Grouping Attributes、批次条件与单个流程的最大任务数。截图中的规则按 ACTION_TYPE 分组，每个 Job 单独触发一次流程。

一条调度规则需要回答四个业务问题

哪些任务适用？Associated Filters 可关联一个或多个 Job Filter。多个 Filter 采用 OR 逻辑，Job 满足其中任意一条即可进入本规则。
进入哪条流程？Workflow 指定匹配任务后续执行的流程定义。应选择与业务类型和现场能力相符的已发布流程。
哪些任务合为一组？Grouping Attributes 按字段值组合分组，值相同的 Job 共用一个 Workflow Instance；不配置时默认按 actionType 分组。
什么时候开始执行？Min Jobs 与 Max Wait 采用 OR 逻辑：达到最低任务数立即启动，或等待达到上限时启动，不要求两个条件同时满足。

分组字段：可使用 containerCode、stationCode、actionType，也支持 extensionData.businessMode 等嵌套路径。字段在 Job 中不存在时按 null 处理，因此缺少相同字段值的 Job 可能被归入同一组。

任务是追加到现有流程，还是新建流程

APPEND追加到运行中的实例存在相同分组键的运行中 Workflow Instance，且当前 Job 数尚未达到 Max Jobs 时，新 Job 加入该实例继续执行。
CREATE_NEW创建新的流程实例没有可追加的同组实例，或现有实例已达到 Max Jobs 时，系统为这批 Job 创建新的 Workflow Instance。
Auto Schedule启用后，系统会自动检查并调度符合规则的 NEW Job；关闭后规则不会被定时调度器执行，但仍可通过 Preview 后的 Confirm Trigger 手动触发一次调度。

CONFIGURATION · C7

Message Config

配置 WCS 向外部系统发送业务消息的方式。

当 Job 完成、失败或取消时，WCS 可以通过 HTTP 回调将处理结果通知 WMS 等外部系统。管理员在这里指定哪些 Job 事件需要通知、由哪个系统接收、发送什么内容，以及回调失败时如何重试。

核心场景 · 将异常结果及时回传上游系统

Job 失败后自动通知 WMS

当符合指定 Filter 的 Job 进入失败状态，WCS 使用 JOB_FAILED 配置生成回调地址、请求头和消息内容，并向 WMS 发送通知。如果网络暂时不可用，系统按设定间隔自动重试，避免现场异常只停留在 WCS 内部。

Job 状态变化→事件与 Filter 匹配→生成回调内容→HTTP POST 通知→失败时自动重试

查看各类 Job 事件的回调配置

哪些 Job 状态会触发消息

JOB_COMPLETEDJob 正常完成向外部系统回传作业已经成功结束。
JOB_FAILEDJob 执行失败向外部系统回传失败结果，便于及时处理异常。
JOB_CANCELLEDJob 被取消通知外部系统停止继续等待该任务结果。
Job Filter选择 Filter 后，只有满足该 Filter 的 Job 才会触发本配置；不选择时，该 Message Type 下的所有 Job 都会发送回调。若不同业务需要发送到不同地址，应分别建立 Filter 和 Message Config。
配置示例

定义接收方、地址与消息内容

示例在 Job 失败时向 WMS_LITE_TRIGGER 发送回调，并通过 Job Filter 仅处理指定业务。Callback URL、Headers 和 Payload Template 中的占位符会在发送时替换为当前 Job 的实际数据。

回调内容由四部分组成

Subscriber标识消息接收方，便于同一事件为不同外部系统维护各自的回调配置。
Callback URL指定接收地址，可使用 ${job.wmsActionId} 等占位符，将 Job 数据动态写入路径。
Headers以 JSON 配置请求头，可动态带入 Tenant、Facility 和时区等调用上下文。
Payload Template定义 HTTP POST 的 JSON 请求体，可引用 ${job.xxx} 和 ${extensionData.xxx} 等业务字段。

发送格式：系统使用 HTTP POST 发送回调，Content-Type 为 application/json。配置前应与接收方确认 URL、请求头、字段名称和占位符数据均符合双方接口约定。

Station Management

查询和维护工作站的基础信息、能力和可用状态。

Station Management 是 WCS 管理端的工作站管理入口。它与 Enter Station 的现场入站动作不同：Enter Station 用于操作员选择并进入工作站，Station Management 用于管理人员确认工作站配置和可用范围。页面提供按 Name、Capabilities、Active Capability、Running Status 和 Station Mode 的筛选条件，列表显示 Name、Capabilities、Active Capability、Linked Location、Running Status、Current User、Enabled 和 Actions，并可通过 Create Station 新建工作站。

核心场景 · 确认任务为什么没有合适的工作站

从工作站配置反查能力匹配

当 WCS Task 长时间等待时，先确认目标工作站是否存在、是否可用，以及它是否具备任务要求的 Capability。若工作站基础信息正常，再继续检查 Capability Workflow Mappings 和现场工作站会话。

查询工作站→确认状态→核对 Capability→检查流程绑定→返回任务追踪
05 · OPERATIONS

从告警、日志到消息发送，排查系统运行问题

Operations 汇集告警处理、日志追溯和消息发送三类排查入口。先在 Alert Management 找到需要处理的告警，再用 Log Query 还原经过，最后用 Message Send Logs 确认外部系统是否收到消息。

OPERATIONS · O1

Alert Management

集中查看和处理 WCS 运行期间产生的告警。

Dashboard 上看到告警数量后，需要在这里找到具体告警、确认它来自哪里，并记录处理结果。

核心场景 · 处理 Dashboard 上出现的告警

从告警数量下钻到具体告警

Dashboard 的 Alert Statistics 显示有未处理告警时，进入 Alert Management，按 Level 和 Status 缩小范围，打开 Detail 查看 Source Entity 和告警内容，再用 Acknowledge、Resolve 或 Ignore 记录处理结果。

页面预览

按级别和状态找到需要处理的告警

页面支持按 Level 和 Status 查询，列表显示 ID、Level、Type、Title、Status、Source Entity、Created Time 和 Actions。

告警有多严重？Level 区分告警级别，Status 显示这条告警当前是否已被处理。
告警来自哪里？Type、Title 和 Source Entity 说明告警的类型、内容和来源对象。
处理结果怎么记录？行内 Detail 查看详情；Acknowledge、Resolve 和 Ignore 用于记录处理结果，操作前先在 Detail 中确认告警内容。
与 Dashboard 的区别Dashboard 只用于快速判断告警数量和严重程度；Alert Management 用于查询具体告警并完成后续处理。
OPERATIONS · O2

Log Query

按事件类型和关联对象还原 WCS 中发生过的状态变化。

需要还原某个 Job 或流程在 WCS 中发生过什么时，从这里按日志类别和关联对象查询。

核心场景 · 还原一次业务变化的经过

从关联对象出发缩小日志范围

先在 Related ID 中填入 Job、Workflow Instance 或 Node Execution 的编号，再选择对应的日志标签页，用 Operation Type 和 Time Range 缩小结果，最后打开 Detail 查看单条记录。

页面预览

按日志类别和关联对象查询

页面包含 Job Lifecycle、Workflow Instance、Node Execution、Device Command、Alert Changes 和 Audit Log 六类标签页，并提供 Time Range、Related ID、Operation Type 等查询条件。列表显示 Time、Operation Type、Job ID、Status Change、Operator、Source 和 Detail。

几类日志分别回答什么问题

Job Lifecycle查看 Job 创建、状态变化和完成过程。
Workflow / Node将流程实例或节点执行记录与相关事件联系起来。
Device Command排查设备指令生成、发送和状态变化。
Audit Log查看需要审计的操作来源、操作人和时间。
查询建议先用 Related ID 锁定 Job、Workflow Instance 或 Node Execution，再根据 Operation Type 和 Time Range 缩小结果。

OPERATIONS · O3

Message Send Logs

追踪 WCS 向外部系统发送的每一条业务消息。

外部系统没有收到 WCS 的任务结果时，先到这里确认消息是否已经发送成功。

核心场景 · 外部系统没有收到任务结果

按 Job ID 确认消息发送结果

WCS 内部任务已经完成，但 WMS 没有更新状态时，按 Job ID 查询发送记录，通过 Status、Retry 和 Fail Reason 判断消息是否发送失败，必要时由管理员查看详情并重新发送。

页面预览

判断消息是否发送成功

列表记录发往外部系统的每条业务消息，可按 Job ID 查询，并显示发送状态、重试次数和失败原因。

消息有没有发出去？Status 显示这条消息的发送结果。
系统有没有重试过？Retry 显示重试次数，次数持续增加说明发送一直没有成功。
为什么失败？Fail Reason 给出失败原因；Detail 可查看单条消息的详细信息。
重新发送前先确认重新发送前，先在 Detail 中确认失败原因已经排除，并确认外部系统确实没有收到该消息，避免产生重复消息。
06 · DEVICE APP

从通信、设备连接和回调记录排查现场链路

Device App 面向系统管理和运维人员，用于判断 WCS 与 RCS、设备客户端或外部回调服务之间是否正常通信。

DEVICE APP · D1

Communication Logs

查看 WCS 与 RCS、设备客户端之间的通信请求。

设备操作没有响应、通信请求失败或接口耗时异常时，先到这里确认是哪个客户端发起了请求，以及请求是否成功完成。

核心场景 · 判断通信请求是否正常

从失败数量下钻到具体请求

先看顶部 Statistics 里的 Failed 是否增加，再按 Client Code 或 Status 缩小范围，打开 Detail 查看单条请求。

页面预览

先看总量，再查具体请求

页面顶部的 Statistics 显示 Total、Success 和 Failed 数量。下方可按 Request ID、Client Code、Client Type 和 Status 查询，列表显示 Request Type、Status、Duration 和 Request Time。

哪个客户端发起了请求？Client Code 和 Client Type 标明请求来自哪个客户端，例如 RCS 回调或具体设备客户端。
请求有没有成功？Status 显示 Success 或失败；Detail 可查看单条请求的详细信息。
接口是不是变慢了？Duration 以毫秒显示耗时，用来判断是个别请求偏慢还是整体变慢。
Real-time页面右侧有 Real-time 开关，默认关闭。需要持续观察新请求时再打开。
DEVICE APP · D2

Client Cache Status

确认设备客户端的缓存与健康状态。

设备客户端或 RCS 连接状态与预期不一致、客户端配置似乎未生效时，用来确认客户端的缓存状态。

核心场景 · 配置改了但客户端行为没变

先确认缓存，再决定是否清除

按 Client Code 找到对应客户端，核对 Health Status、Consecutive Failures 和 Last Accessed。确认影响范围后，再对单个客户端执行 Evict。

页面预览

按客户端查看缓存与健康状态

页面支持按 Client Code、Health Status 和 Protocol Type 查询。列表显示 Client Code、Client Class、Protocol Type、Engine State、Health Status、Last Health Check、Consecutive Failures、Created At 和 Last Accessed。

Refresh重新读取当前缓存状态，用于确认页面显示的是最新数据。
Evict清除所选客户端的缓存，缓存会在下次使用时重新建立。
Evict All清除全部客户端的缓存，影响范围最大。
清除缓存Evict 和 Evict All 会让客户端在下次使用时重新建立连接。请先确认影响范围，再操作；优先使用 Evict 处理单个客户端。
DEVICE APP · D3

Device/RCS Debug

在正式配置前测试 RCS 与设备的连接。

RCS 或现场设备无法连接、指令无法下发时，用来测试 RCS 与设备的连接。该页面主要供实施和运维人员诊断。

核心场景 · 现场设备连不上

先选类型，再测试连接

进入 Device/RCS Debug Console，按对象选择 RCS Clients 或 Equipment Clients，在 Select Client Type 中选好类型后再测试。

页面预览

按对象分为两个页签

页面是 Device/RCS Debug Console，用于在 facility-app 配置前测试连接。RCS Clients 测试 RCS 客户端，Equipment Clients 测试设备客户端。

真实连接测试会真实连接现场设备。请先确认客户端类型和影响，再进行测试。
DEVICE APP · D4

Callback Records

查看外部系统回调 WCS 的处理结果。

外部设备或系统已经回调，但 WCS 没有产生预期业务结果时，用来查看回调状态、重试次数和最近一次错误。

DEVICE APP · D5

Maintenance Tools

对 RCS 与设备做状态检查、问题查询和现场干预。

实施或运维人员需要对设备做维护检查时进入。先选择要维护的对象，再按需要查看状态、查询问题；确需干预现场时，再使用 Interventions。

核心场景 · 先看状态，再决定是否干预

按 Monitoring、Diagnostics、Interventions 的顺序使用

先用 Monitoring 看整体状态，再用 Diagnostics 按容器、库位或任务编号查原因。只有确认没有进行中的作业、且确需处理时，才使用 Interventions。

页面预览

按功能分组的维护入口

页面按 RCS Client 和 Equipment 两类对象切换，选中后显示名称、编码和连接状态。RCS Client 下的功能分为 Monitoring、Diagnostics 和 Interventions 三组，每项功能点击 Execute 才会执行。

MonitoringSystem Status、Robot List、Station Queue Status，用于查看状态。
DiagnosticsContainer Location Search、Location Search、Container Error Search、Task Error Search，按输入的容器、库位或任务编号查询。
InterventionsNotify First to Leave、Emergency Stop 和 Resume，会直接影响现场运行。
CAUTIONInterventions 标有 CAUTION，Emergency Stop 为 STOP 按钮。请先用 Monitoring 和 Diagnostics 确认情况，并在确认没有进行中的作业后再使用。
