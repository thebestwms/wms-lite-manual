01

入库与上架

根据客户对月台周转、收货差异和库位使用的要求，决定收货任务怎样推进。

流程要求

不需要系统记录完整的月台作业步骤

Skip Receive Steps 可按客户跳过 Dock Check In 或 Offload。适合不在系统中管理签到或卸货步骤的业务；LP Setup 仍会保留，因为它负责建立实际收货的 LP。

时效要求

货物确认后立即上架，还是整单收完后统一上架

Put Away Mode 选择 DURING_RECEIVING 时，完成 LP Setup 后即可生成上架任务；选择 AFTER_RECEIVING 时，关闭收货任务后再统一生成。

完成标准

收货单何时才算完成

Receipt Close Timing 可在收货任务完成时关闭 Receipt，也可以等到上架完成后关闭。后者适用于客户把“货物已入库位”作为入库完成标准的情况。

数量差异

供应商实到数量允许超过预计数量

Receive Qty Checks 按 Receipt Type 控制是否允许超收和最大比例。例如退货收货可以接受一定差异，常规采购收货则可以设置为不允许超收。

容器规则

一个 LP 是否可以同时装载多个 SKU

Allow LP Mixed Item 开启后允许同一 LP 混放不同商品；实际存放仍需满足 Location、Container Type 等其他规则。

库位推荐

系统按照什么顺序寻找上架库位

Put Away Strategies 按优先级逐条匹配，例如优先进入已有相同商品的库位，或优先选择空库位。数值越小的策略越先执行。

02

出库与拣货

根据客户对库存周转、订单变更和拣货效率的要求，控制分配与任务执行顺序。

库存周转

出库时应优先使用哪一批库存

Default Shipping Rule 是默认库存分配规则。选择 FIFO 时，系统按库存创建时间由早到晚进行分配，用于落实先进先出的周转要求。

订单组织

按什么时间范围归集订单或波次

Time Window 可按日、周、月等时间窗口对订单进行分组；不选择时间窗口时，订单不按该维度归集。

订单变更

客户最晚可以在什么阶段取消订单

Allow Order Cancellation Before 设置允许取消的状态边界。边界越靠前，订单进入拣货、装箱或装车后越早停止接受取消。

库位利用

优先释放被少量库存占用的库位

Enable Depleted Location 开启后，分配时优先选择本次拣完即可清空库位的库存，减少零散库存长期占用库位。

拣货路径

不同仓库采用不同的拣货排序

Pick Sort Rules 定义拣货任务的排序方式，并可按 Facility 配置覆盖规则，使同一客户在不同仓库采用各自的作业顺序。

批次控制

拣货时严格执行 Shipping Rule 或放宽 Lot No 校验

Force Pick By Shipping Rule 强制校验库存是否符合订单规则；Skip LotNo Validation 则用于决定是否跳过订单指定 Lot No 与实际库存的匹配检查。

03

自动化与数据连接

根据客户的设备范围和数据交换要求，决定任务发送、事件通知及扩展资料的处理方式。

设备执行

指定类型的仓储任务由自动化设备完成

Enable WCS 开启后，还需在 Task Config 中启用对应任务类型。两项条件同时满足时，相关 Task Action 才会发送到 WCS。

结果通知

客户系统需要及时接收关键业务结果

Webhook Channels 可订阅订单发货、收货关闭和库存调整事件，并配置回调地址、启用状态及最大重试次数。

客户化资料

标准字段不足以承载客户自己的参考信息

Dynamic Field Mapping 可为 Item、Receipt、Order、明细和 Inventory 配置扩展字段名称，用于页面展示、导入导出、接口同步和精确查询。

MDM · ITEM

统一维护仓库识别、追踪和处理商品所需的主档

Item 以租户内唯一的 SKU 识别商品，并记录当前 Customer、商品类型、条码、序列号、批次效期、计量单位、托盘配置及行业扩展资料。业务单据和库存通过稳定的 Item ID 持续引用商品。

页面预览

Item 列表集中查看与管理商品主档

通过列表查询已有商品，并查看 SKU、Customer、Type、Status 等主要资料；需要新建或维护商品时，可从这里进入对应操作。

核心场景

新商品接入仓库

仓库开始接收一个新商品前，先确认租户内是否已有相同 SKU；没有可复用主档时，再确定客户归属和商品类型，补充识别与追踪要求，并根据实际包装和码放方式维护 UOM 与 Pallet Config。

  1. 确认商品身份查询 SKU，确定 Customer 与 Type
  2. 设置追踪要求维护条码、序列号、批次与效期
  3. 描述包装层级配置 UOM、尺寸、重量和价值资料
  4. 进入仓储业务供入库、出库、库存和任务引用

Outbound Order 是出库作业的起点。它记录本次订单属于哪个客户、需要发出哪些商品和数量、送往哪里、由谁承运以及计划何时完成；库存锁定、拣货、包装和装车都以这些订单资料为依据。

从列表掌握待处理订单与当前进度

顶部汇总区显示 Imported、Processing、Shipped 和 Total；订单列表进一步显示 Order Plan 与 Status，用于判断订单是否尚待处理、库存承诺受阻、已经进入计划或完成发运。

核心场景

客户要求仓库把一批商品发往指定收货地址

操作人员先选择 Customer，确认订单类型与运输要求，再填写 Ship To Address 和计划时间，最后添加 SKU Lines。订单保存后形成出库需求，但此时还没有扣减库存；后续 Inventory Commitment 才会为订单匹配并锁定可用库存。

订单归属谁要发货

Customer 确定订单归属，并影响后续库存分配策略和 Load 分组。

发货内容发什么、发多少

SKU Lines 记录 Item、UOM、Title 和 Qty，作为库存匹配与数量换算依据。

履约要求发到哪里、如何运输

Address、Carrier、Ship Method 和时间字段共同描述交付要求。

Customer订单所属客户，决定可选商品及适用的库存分配策略。
Retailer订单对应的零售渠道或门店体系。
Order Type出库业务类型，如 Regular Order。
Reference No客户或上游系统提供的业务参考编号，用于查询与对账。
Sales Order No关联的销售订单编号。
PO No关联的采购订单编号。
Batch No出库订单的批次编号，用于归集同批导入或同批处理的订单。
Master Tracking No整票货件或主包裹的总追踪编号。
Source订单来源，如页面手工创建或接口导入。
Signature Type承运交付时要求的签名服务类型。

Single QTY标识订单是否属于单件数量场景，由系统根据订单内容显示。
运输安排

Carrier 表示实际承运商，Ship Method 决定订单采用的运输场景：Truckload（整车）、Less Than Truckload（零担）、Will Call（客户自提）或 Small Parcel（小包裹）。Delivery Service、Freight Term 和运输单号用于补充具体交接要求。

履约时间

Schedule Date、Ship Not Before / Later 和 Appointment Time 用来描述计划作业及允许发货的时间窗口；Shipped Time、Canceled Date 等由后续状态记录实际结果。

Address

Ship From 表示本次发货方，Ship To 表示实际收货目的地，Bill To 用于账单资料。选定后地址内容随订单保存，后续主档修改不会改变该订单。

SKU Lines

SKU 确定商品，UOM 与 Qty 表示需求数量，Title 限定货权。Inventory Commitment 会按照这些条件匹配并锁定库存；保存订单本身不会直接扣减库存。

OUTBOUND · INVENTORY COMMITMENT

在订单进入拣货前，确认库存是否能够兑现需求

Inventory Commitment 将 Outbound Order 的需求与当前可用库存进行匹配。它先显示订单行的库存缺口，再由用户执行锁定；锁定结果会直接更新订单状态，并决定订单能否继续进入拣货计划。

核心场景

先看缺口，再决定哪些订单可以进入履约

当多个订单同时等待出库时，操作人员可以先预览每个 SKU 的需求、已锁定数量和缺口数量，判断库存不足会影响哪些订单，再执行 Commit。库存充足的订单进入 Committed；只有部分库存可用时进入 Partial Committed。

OUTBOUND · ORDER PLANS

把待出库订单组织成可执行的拣货计划

Order Plans 将一个或多个已承诺库存的订单打包到同一个计划中，并指定该计划使用的 Pick Method、Pick Mode 和 Task Priority。计划创建后释放，系统据此生成拣货任务。

当一批订单完成库存锁定后，计划员需要决定这些订单的拣货策略——是逐单拣还是合并拣、用人工推车还是 AGV，以及优先级如何。Order Plans 就是这个决策的执行入口。

Pick Method

Pick by AGV由 AGV 将货架送至固定工位，采用货到人方式拣货。

INVENTORY · INVENTORY

查询当前库存数量，并定位货物所在的库位与容器

Inventory 是仓库的库存查询台账。它将商品、数量、状态、Location、LP 以及关联的收货单、订单和 Load 汇集在同一入口，帮助操作人员确认当前库存处于哪个作业阶段、存放在哪里。

INVENTORY · INVENTORY LOCK

在库存真正拣出前，为订单保留可履约数量

Inventory Lock 记录出库订单或装配任务已经预留的库存，避免同一批可用量被重复分配。锁定只影响后续订单还能分配多少，不会立即减少 Inventory 页面中的库存台账数量。

核心场景

多个出库订单需要同一 SKU，先为准备履约的订单保留库存

当可用库存无法同时满足所有订单时，仓库先决定本轮需要处理的订单并执行 Commitment。系统为这些订单建立 Lock，后续订单便不会重复使用已预留的数量；若客户取消订单或仓库重新安排履约顺序，再通过 Rollback 释放占用并重新分配。

数量关系：Open Inventory 100 EA − Active Lock 30 EA = 其他订单仍可分配 70 EA。Inventory 台账仍显示仓库现有 100 EA，直到实际拣货后库存状态才发生变化。

Commitment 执行库存分配，Inventory Lock 保存分配结果

用户不会在 Inventory Lock 页面手工建立锁定。锁定主要从 Outbound Inventory Commitment 产生；Order Dispatch 自动执行 Commitment 时，也会走同一套锁定逻辑。

INVENTORY · LP

用一个可扫描编号，识别并追踪整托、整箱或整料箱库存

LP（License Plate）是托盘、纸箱、周转箱等库存载体在系统中的编号。它把库存、库位和作业状态关联起来，让操作人员无需逐条识别库存，即可通过扫描 LP 完成收货、上架、拣货、打包和装车中的确认与追踪。

核心场景

货物在仓库中不断更换位置和载体，LP 保留可追踪的库存归属

收货后，库存先装入托盘或容器 LP；上架时扫描 LP，将整组库存移动到目标库位。出库过程中，库存又可能进入拣货料箱、纸箱和外层发运单元。系统通过每个阶段的 LP，持续确认这批库存在哪里、装在哪个载体中，以及正处于哪个作业阶段。

入库与存储整托或整箱上架

库存装入 LP 后，通过标准上架或移动作业，将 LP 与其中的库存一起更新到目标库位。

拣货与发运扫码识别作业载体

拣货库存进入料箱，打包后进入纸箱；后续打包、装车和发运继续扫描对应 LP。

包装层级纸箱归集到外层单元

Parent LP 记录子箱与外层发运 LP 的包含关系，便于按整组识别纸箱和关联库存。

INVENTORY · ADJUSTMENT

通过可审批的调整单，纠正库存数量、位置和属性差异

Adjustment 不只用于修正库存数量。当库存被记录在错误的 LP 或库位，或者状态、货权、质量分类、批次及日期等信息有误时，也可以通过调整单进行更正。保存单据不会立即改变库存，只有审批成功后，整张 Adjustment 才会执行并留下可追溯记录。

核心场景

盘点发现实际库存与系统数量不一致

操作人员先找到对应库存，创建 Adjust Qty 并将目标数量填写为 18 EA。复核人员确认差异原因后批准单据，库存才从 15 EA 更新为 18 EA，同时生成 Inventory Activity。这样既纠正当前库存，也保留是谁、因为什么原因进行调整的记录。

Adjustment 的创建来源 除了操作人员在网页中创建，盘点和部分库存业务也会由系统生成调整单。
人工创建现场发现库存问题

发现破损、丢失、找回、收货差异或资料错误时，由操作人员创建 Adjustment。

盘点自动生成Cycle Count 出现差异

Count Result 审批后，系统自动创建并批准相应的 Adjustment。

其他业务自动生成LP 删除或 Assembly

删除仍含库存的 LP 时，系统自动生成调减单；Assembly 生成的调整单为 NEW，仍需人工审批。

INVENTORY · MIN/MAX SETTING

拣货区库存不够时，自动从储存区补货

Min/Max Setting 为每个 SKU 设置拣货区的最低和最高库存水位。当目标区域库存低于 Min Qty 时，系统创建 Replenishment Task，指导操作员从储存区搬运库存至拣货区。任务创建不会立即改变库存，完成 Collect 与 Drop 后库存位置才更新。

核心场景

拣货位库存即将耗尽，提前安排补货

某 SKU 每日出库量为 200 EA，但拣货区只能存放 100 EA。若等到拣货员发现库位已空再人工安排补货，订单会停在现场等待。配置 Min/Max 规则后，系统在库存低于 Min Qty 时生成补货任务，让操作员提前从储存区搬货。

CYCLE COUNT · COUNT TICKETS

先确定盘点对象与规则，再把范围拆成现场任务

Count Ticket 是一次盘点的计划单。它记录为哪个客户盘点、按库位还是商品确定范围、采用哪种计数方法，以及是否隐藏系统数量。保存 Ticket 不会改变库存；创建 Count Task 后，现场人员才开始执行盘点。

核心场景

对高频拣货区安排一次不受系统数量影响的抽盘

仓库希望核对某客户拣货区的实物数量时，可以建立日常盘点 Ticket，按 Location 选择需要抽查的库位，采用 Simple Qty Count 并开启 Blind Count。一个 Ticket 可以拆成多个 Count Task，分别交给不同操作员或区域执行。

按业务目的选择范围、计数方式和执行要求

先选择 Customer，再确定 Count Type、Count Method 和 Count Category；页面会根据选择启用对应的 Count Scope。Schedule Date 和 Target Completion Date 用于安排执行窗口，Blind Count 决定现场是否可见账面数量。

Count Type范围按什么展开

By Location 选择库位并展开其中库存；By Item 选择商品并覆盖其所在库位；By Item + Location 直接指定精确组合。

Count Method现场按什么单位清点

Simple Qty / Piece 用于数量盘点，Case 按箱数比较，Pallet / Simple LP 用于托盘或 LP 维度核对。

Count Category为什么发起这次盘点

Daily / Cycle 走标准流程；Full 自动覆盖客户全部库存；Picking Exception 与 Full Air ROB Count 由特定场景自动建任务。

Blind Count是否隐藏系统数量

开启后不显示 System Qty 与 Expected Qty，避免操作员参考账面数填写；SKU、LP 和 Location 仍然可见。

盘点期间不冻结库存：收货、拣货和库存移动可以继续进行。每条盘点 Action 提交时，系统实时查询当时库存并计算差异，因此结果反映的是提交瞬间的账实情况。
